3. テーブル定義

PostgreSQL (Supabase) を使用する。テーブルはT-01〜T-29のうち実働24テーブルとする（T-02, T-05, T-07, T-24, T-25は基本設計書で廃止済みのため欠番。6.2節参照）。共通方針は以下のとおり。

  • idは全テーブルBIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY（T-21のみkey TEXTを主キーとする）。
  • created_atは全テーブルTIMESTAMPTZ NOT NULL DEFAULT now()。updated_atは更新が発生しうるテーブルにのみ付与し、アプリケーション側で更新時にnow()を設定する（T-15〜T-20, T-27〜T-29は追記専用のためupdated_atを持たない）。
  • コード値（role, status, type, kind, scope_type等）はCHECK制約で許容値を担保する。
  • JSONB項目（tags, options, correct_answer, response, findings, weak_questions, completed_node_ids等）のスキーマは各表の下に示す。
  • 全テーブルでRow Level Security（RLS）を有効にする（ALTER TABLE ... ENABLE ROW LEVEL SECURITY;）。アプリケーションはasyncpgで直接接続するため通常アクセスの権限判定（5章）はAPI層で行うが、Supabaseの他経路（PostgREST等）からの意図しない参照を遮断する多層防御として全テーブルRLSを必須とする（Keirekiと同方針）。
  • スキーマ定義はbackend/database.pyのSCHEMA定数（CREATE TABLE IF NOT EXISTS文の集合）に集約する。
T-08 material_revisions のカラムに関する整合（基本設計書からの補足）: 基本設計書8.5節はbody_snapshot・formatを「変更後のmaterials.body・materials.formatの全文スナップショット」と説明しているが、6.2節(7)のとおりv1.11でmaterials.body・materials.formatは廃止され、目次構造・各ページの本文はT-23 material_nodesへ移管されている。A-20（書き戻し）は教材1件分のフロントマター＋見出しツリー＋本文＋問題ブロックを含むテキスト全体を受け取る（7章参照）ため、本書ではbody_snapshotを「A-20/A-31呼び出し時に送信された教材ソーステキスト全体（8.3節のフロントマタースキーマに従うテキスト）のスナップショット」と定義し直す。format列は個々のページごとに持ちうる値（T-23.format）になったため本テーブルからは削除し、代わりに差分の主体を示すdiff_kind（'source'固定。将来A-17由来のメタデータ変更にも本テーブルを流用する可能性に備えた列だが、v1.0時点ではA-20/A-31起因の行のみを記録するため常に'source'）は設けず、8.5節の方針どおり「A-17（メタデータのみの変更）はT-08の対象外」を維持する。この読み替えにより実装上の不整合は生じない。

3.7 CREATE TABLE 例

database.pyのSCHEMA定義に全24テーブルのDDLを記載する。代表として、自己参照ツリー（T-23）・部分インデックスによる条件付き一意性（T-26）・JSONB既定値とGINインデックス（T-06）・複数CHECK制約の組み合わせ（T-04）を示す（他テーブルも同一の書式）。

-- T-04 project_memberships
CREATE TABLE IF NOT EXISTS project_memberships (
    id          BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id  BIGINT NOT NULL REFERENCES projects(id),
    user_id     BIGINT NOT NULL REFERENCES users(id),
    role        TEXT NOT NULL DEFAULT 'learner'
                CHECK (role IN ('admin', 'editor', 'learner')),
    assigned_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
    status      TEXT NOT NULL DEFAULT 'invited'
                CHECK (status IN ('invited', 'active', 'declined')),
    joined_at   TIMESTAMPTZ,
    left_at     TIMESTAMPTZ,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (project_id, user_id)
);
CREATE INDEX IF NOT EXISTS idx_project_memberships_user_id ON project_memberships (user_id);
ALTER TABLE project_memberships ENABLE ROW LEVEL SECURITY;

-- T-06 materials
CREATE TABLE IF NOT EXISTS materials (
    id                     BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    project_id             BIGINT NOT NULL REFERENCES projects(id),
    title                  TEXT NOT NULL,
    description            TEXT,
    tags                   JSONB NOT NULL DEFAULT '[]',
    created_by             BIGINT NOT NULL REFERENCES users(id),
    status                 TEXT NOT NULL DEFAULT 'draft'
                           CHECK (status IN ('draft', 'published')),
    sort_order             INTEGER NOT NULL DEFAULT 0,
    attempt_scope          TEXT NOT NULL DEFAULT 'material'
                           CHECK (attempt_scope IN ('material', 'chapter', 'section', 'page')),
    retake_scope           TEXT NOT NULL DEFAULT 'all'
                           CHECK (retake_scope IN ('all', 'wrong_only')),
    default_feedback_style TEXT NOT NULL DEFAULT 'show_answer'
                           CHECK (default_feedback_style IN ('show_answer', 'review_only', 'hint_only')),
    ai_context              TEXT,
    grading_mode             TEXT NOT NULL DEFAULT 'ai' CHECK (grading_mode IN ('ai', 'manual')),
    created_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_materials_project_id ON materials (project_id);
CREATE INDEX IF NOT EXISTS idx_materials_tags ON materials USING GIN (tags jsonb_path_ops);
ALTER TABLE materials ENABLE ROW LEVEL SECURITY;

-- T-23 material_nodes（自己参照ツリー）

5.2 require_project_role の実装

ROLE_RANK = {"learner": 1, "editor": 2, "admin": 3}

async def require_project_role(project_id: int, min_role: str):
    async def checker(request: Request) -> User:
        user = await require_auth(request)
        if user.role == "admin":
            return user   # システム全体のadminは常に許可（保守目的）
        row = await conn.fetchrow(
            """SELECT role FROM project_memberships
                WHERE project_id = $1 AND user_id = $2
                  AND status = 'active'""",
            project_id, user.id)
        if row is None or ROLE_RANK[row["role"]] < ROLE_RANK[min_role]:
            raise HTTPException(403, detail="この操作を行う権限がありません")
        return user
    return checker

status != 'active'（招待中invited・辞退declined）のメンバーはロールを問わず不許可となる。left_at IS NOT NULL（削除済み）の行はそもそもstatusを条件に含めても除外されない可能性があるため、実装上はWHERE ... AND status = 'active' AND left_at IS NULLとする（削除時にstatusは変更しないため。4.2節A-13参照）。

5.3 require_material_access の実装（受講対象者判定）

基本設計書7.3節が定める「対象教材の受講対象者」のOR条件を1つの依存関数に集約する。個々のルーターが判定ロジックを重複実装しないようにするための共通化である。

async def require_material_access(material_id: int):
    async def checker(request: Request) -> User:
        user = await require_auth(request)
        if user.role == "admin":
            return user
        material = await fetch_material_scope_row(material_id)  # project_id, status
        # 条件1: 教材が紐づくプロジェクトの現役メンバー（受講者以上）
        is_project_member = await has_active_project_role(
            material["project_id"], user.id, min_role="learner")
        if is_project_member:
            return user
        # 条件2: 配信設定（T-11 assignments）で個人指定されている
        is_individual_target = await conn.fetchval(
            """SELECT EXISTS(
                 SELECT 1 FROM assignments
                  WHERE material_id = $1 AND scope_type = 'individual'
                    AND scope_id = $2)""",
            material_id, user.id)
        if is_individual_target:
            return user
        # 条件3: status='accepted' で共有された先のプロジェクトの現役メンバー
        shared_project_ids = await conn.fetch(
            """SELECT shared_to_project_id FROM material_project_shares
                WHERE material_id = $1 AND status = 'accepted'""",
            material_id)
        for row in shared_project_ids:
            if await has_active_project_role(
                    row["shared_to_project_id"], user.id, min_role="learner"):
                return user
        raise HTTPException(403, detail="この教材の受講対象ではありません")
    return checker
なぜ3条件のORが必要か: プロジェクトのローカルロール（5.2節）だけでは、プロジェクトのメンバーでない社員を個人指定で受講対象に加える配信設定（F-09）を表現できない。また教材のプロジェクト間共有（F-26）も、共有先プロジェクトのメンバーという別経路でのアクセスを許可する必要がある。この3条件は「教材が紐づく1つのプロジェクトのメンバーであること」を必須としない設計であり、必ずどれか1つを満たせばよい。

5.5 プロジェクト離任後の猶予期間判定

基本設計書5.25節の猶予期間ロジックを、5.3節のhas_active_project_roleを拡張する形で実装する。「現役メンバー」または「削除から猶予日数以内」のいずれかを満たせば受講権限を継続する。

async def has_active_project_role(project_id: int, user_id: int, min_role: str) -> bool:
    row = await conn.fetchrow(
        """SELECT role, status, left_at FROM project_memberships
            WHERE project_id = $1 AND user_id = $2""",
        project_id, user_id)
    if row is None:
        return False
    if row["status"] == "active" and row["left_at"] is None:
        return ROLE_RANK[row["role"]] >= ROLE_RANK[min_role]
    if row["left_at"] is not None:
        grace_days = await get_setting_int(
            "project_leave_grace_period_days", default=30)
        if row["left_at"] + timedelta(days=grace_days) >= datetime.now(timezone.utc):
            # 猶予期間中は「受講者」相当のアクセスのみ継続する（編集権限は即時失効）
            return min_role == "learner"
    return False
猶予期間中は受講権限のみ継続する: 基本設計書5.25節の設計判断のとおり、ロール降格そのものは猶予期間の対象外とし、プロジェクトから削除された場合のみ猶予期間が発生する。上記実装ではleft_atが設定された行に対してはmin_role == "learner"のときのみtrueを返すことで、「猶予期間中でも教材の新規編集はできない（即時失効）が、既に配信された教材の閲覧・受講は継続できる」という非対称な扱いを表現している。

       (SELECT COUNT(*) FROM material_nodes n WHERE n.material_id = m.id AND n.kind = 'chapter') AS chapter_count,
       (SELECT COUNT(*) FROM material_nodes n WHERE n.material_id = m.id AND n.kind = 'page') AS page_count,
       m.updated_at
FROM materials m
JOIN projects p ON p.id = m.project_id
WHERE m.status = 'published'
  AND ($1::text IS NULL OR
       m.title ILIKE '%' || $1 || '%' OR
       m.description ILIKE '%' || $1 || '%' OR
       EXISTS (SELECT 1 FROM material_nodes n
                WHERE n.material_id = m.id AND n.title ILIKE '%' || $1 || '%'))
  AND ($2::jsonb IS NULL OR m.tags @> $2)                 -- tags（AND条件）
  AND ($3::bigint IS NULL OR m.project_id = $3
       OR EXISTS (SELECT 1 FROM material_project_shares s
                   WHERE s.material_id = m.id AND s.shared_to_project_id = $3
                     AND s.status = 'accepted'))            -- project_id（共有先も含む）
ORDER BY m.updated_at DESC
LIMIT $4 OFFSET $5;

6.4 A-45/A-46 受講状況ダッシュボードの集計

実装はrouters/dashboard.py。scopeパラメータが"company"なら全社員・全教材、"project:{id}"なら当該プロジェクトの現役メンバー（status='active' AND left_at IS NULL）かつ当該プロジェクトの配信設定を対象に集計する。

-- 対象範囲内の必修受講率（scope=project:{id} の例。$1=project_id）
WITH target_users AS (
    SELECT user_id FROM project_memberships
     WHERE project_id = $1 AND status = 'active' AND left_at IS NULL
),
target_assignments AS (
    SELECT a.material_id, a.due_at, a.id AS assignment_id
      FROM assignments a
     WHERE a.scope_type = 'project' AND a.scope_id = $1 AND a.required = true
)
SELECT ta.material_id,
       COUNT(tu.user_id) AS target_count,
       COUNT(ep.user_id) FILTER (WHERE ep.status = 'completed') AS completed_count,
       COUNT(qa.id) FILTER (WHERE qa.passed = true) AS pass_count
  FROM target_assignments ta
  CROSS JOIN target_users tu
  LEFT JOIN enrollment_progress ep
         ON ep.material_id = ta.material_id AND ep.user_id = tu.user_id
  LEFT JOIN LATERAL (
         SELECT * FROM quiz_attempts
          WHERE material_id = ta.material_id AND user_id = tu.user_id
            AND mode = 'graded' AND submitted_at IS NOT NULL
          ORDER BY attempt_no DESC LIMIT 1
       ) qa ON true
 GROUP BY ta.material_id;

未受講者一覧（A-46）は上記のtarget_usersからenrollment_progress.status != 'completed'（またはenrollment_progress行が存在しない）ユーザーを抽出し、due_atを付与して返す。

6.5 A-44 誤答問題抽出出題のロジック

7.1 CLIトークン発行フロー（A-62〜A-63）

7.2 フロントマター・本文パース（material_parser.py、A-20/A-31が使用）

A-20（PUT /api/materials/{id}/source）が受け取るテキストは、基本設計書8.3節のスキーマに従う。パースは以下の順で行う。

受験後アンケート（T-26〜T-29）はテキスト形式の対象外: 基本設計書8.3節のフロントマタースキーマ・問題ブロック形式のいずれにもアンケート定義は含まれない。アンケートの設置・設問編集はS-05の編集モーダル（A-78/A-79、4.3節）からのみ行い、Claude Code連携（A-19/A-20）では取得・更新できない。教材の目次・問題はF-05（本節）とS-05の両方から編集できるのに対し、アンケートはS-05のみで完結する点に注意する。
  1. フロントマター分離: 先頭が---で始まる場合、次の---行までをYAMLとしてパースし、id, project_id, tags, title, description, format, status, sort_order, attempt_scope, retake_scope, default_feedback_style, ai_context, grading_modeを取得する（PyYAMLのsafe_loadを使用。任意コード実行を伴うyaml.loadは使わない）
  2. 見出し行の走査: フロントマター以降の本文を行単位で走査し、format='markdown'なら#/##/###で始まる行、format='html'なら<h1>/<h2>/<h3>タグを見出しとして検出する。検出のたびに現在の階層状態（現在の章ノード・現在の小見出しノード）を更新する: #/<h1>→新しい章を開始し小見出し状態をリセット、##/<h2>→現在の章の下に小見出しを開始、###/<h3>→現在の小見出し（あれば）または現在の章（無ければ）の下にページを開始する
  3. ノードID注記の読み取り: 各見出し行の直後に<!-- node:123 -->があれば、そのノードは既存ノード（id=123）の更新として扱う。注記が無ければ新規ノードとして扱う（書き戻し時にIDを採番）
  4. ページ本文の抽出: ###見出し（＋ノード注記）の直後から、次の見出し行またはテキスト末尾までを、当該ページのbody候補とする。この範囲内に含まれる```questionフェンスブロック（Markdown）または<!-- question ... -->コメント（HTML）はbodyから取り除き、問題ブロックとして別途抽出する（本文と問題の分離）
  5. 問題ブロックのパース: 各問題ブロックをYAMLとしてパースし、id, type, prompt, options, correct_answer, scoring_criteria, code_language, required, is_critical, feedback_style, pool_group, score_unit, grading_modeを取得する。typeごとの必須フィールド検証（基本設計書8.3節の表）をPydanticモデルで行い、不足時は422で該当ブロックの行番号を含めて返す
  6. content_kindの自動判定: ページにbody候補があり問題ブロックが無ければ'explanation'、逆なら'quiz'、両方あれば'mixed'。どちらも無ければ422（「説明文・問題のいずれか一方は必須」）
見出しレベルの逸脱時の扱い: 章（#）を開始せずにいきなり##や###が出現した場合、あるいは小見出し（##）を経由せず章の直下にページ（###）が続く場合は、後者（章に直接ぶら下がるページ）は基本設計書8.3節が示す正当な構成として許容する。前者（章の開始前に##/###が出現）はパースエラーとし、422 {"detail": "本文の先頭は章（#見出し）から始めてください"}を返す。

7.3 書き戻し処理（A-20 PUT /source の実装）

1回の呼び出しでフロントマターのメタデータ・目次ツリー全体・全問題をまとめて全置換する。処理はトランザクション内で行う。

  1. 7.2節の手順でリクエストボディをパースし、パース結果（ノード配列＋各ページの問題配列）を得る
  2. フロントマターのidが指定されていればT-06 materialsの対象行、無ければA-16相当の新規作成として扱う。project_idが現在のmaterials.project_idと異なる場合は400（4.3節A-20の注記参照。プロジェクト付け替えはA-17を使う）
  3. materials行のメタデータ（title, description, tags, status, sort_order, attempt_scope, retake_scope, default_feedback_style, ai_context, grading_mode）を更新する
  4. ノードの全置換: 送信されたノード配列のうちノードID注記があるものはUPDATE material_nodes SET ... WHERE id = ?、無いものはINSERTで新規採番する。今回のリクエストに含まれなかった既存ノードは削除する（CASCADE削除により配下の問題・受験記録は残らない点に注意。9.1節エラーハンドリングで警告を検討）
  5. 問題の全置換: 各ページ（葉ノード）に紐づく問題ブロックについて、A-31と同一のロジック（送信内容で当該node_idの問題を全置換）を適用する
  6. T-08 material_revisionsへ1行追加する（7.4節）
  7. コミット後、新規採番されたノードID・問題IDを含む最新のソーステキスト（7.2節と逆の手順で組み立てる）をレスポンスとして返す。Claude Codeは次回のGET（A-19）を待たずとも、このレスポンスから新規IDを把握できる
全置換のリスクと運用上の注意: ノードの全置換は、Claude Codeが取得（A-19）した内容の一部を誤って欠落させたまま書き戻した場合、その欠落した章・ページが削除されてしまう。これはA-31（画面からの問題一括更新）と同じ全置換セマンティクスであり、意図的な設計（取得→修正→書き戻しの往復を単純に保つため）である。既存の受験記録（quiz_attempts, answers）はノード自体が削除されるとCASCADEで失われるため、公開済み（status='published'）の教材で受験記録が既に存在するノードを削除するリクエストは、確認なしに実行せず、レスポンスに{"warnings": ["ページ「...」を削除すると、既存の受験記録が失われます"]}を含めて返す（処理自体は実行するが警告を返す。要件定義書のREQ-F-02が「往復できること」を最優先要求としているため、書き込みブロックによる往復の阻害は避ける）。

7.4 changed_via の判定と改訂履歴

基本設計書8.5節のとおり、changed_viaはJWTペイロードのtoken_typeクレームで機械的に判定する（'session'→'web'、'cli'→'claude_code'）。change_summaryの自動生成ルールは以下のとおり。

8.3 スタックジョブ・スイープの実装（job_sweep.py）

# backend/job_sweep.py
STUCK_THRESHOLD = timedelta(minutes=10)
SWEEP_INTERVAL = timedelta(minutes=5)

async def sweep_stuck_jobs():
    cutoff = datetime.now(timezone.utc) - STUCK_THRESHOLD

    # T-16〜T-18: requested_at が古く、内容カラムが未設定の行
    for insight in await conn.fetch(
            """SELECT id, material_id FROM ai_material_insights
                WHERE requested_at < $1 AND suggestions IS NULL""", cutoff):
        asyncio.create_task(run_ai_insights_job(insight["id"], insight["material_id"]))

    for feedback in await conn.fetch(
            """SELECT id, user_id FROM ai_personal_feedback
                WHERE requested_at < $1 AND content IS NULL""", cutoff):
        asyncio.create_task(run_ai_personal_feedback_job(feedback["id"], feedback["user_id"]))

    for report in await conn.fetch(
            """SELECT id, scope_type, scope_id FROM ai_org_reports
                WHERE requested_at < $1 AND content IS NULL""", cutoff):
        asyncio.create_task(run_ai_org_report_job(report["id"], report["scope_type"], report["scope_id"]))

    # T-14: submitted_at が古く、ai_score_pct が未設定の記述式・code回答（grading_mode='ai'のみ対象）
    for answer in await conn.fetch(
            """SELECT a.id, a.attempt_id, a.question_id FROM answers a
                 JOIN quiz_attempts qa ON qa.id = a.attempt_id
                 JOIN questions q ON q.id = a.question_id
                WHERE qa.submitted_at < $1 AND a.ai_score_pct IS NULL
                  AND q.type IN ('free_text', 'code')
                  AND COALESCE(q.grading_mode,
                      (SELECT grading_mode FROM materials WHERE id = qa.material_id)) = 'ai'""",
            cutoff):
        asyncio.create_task(run_ai_grading_job(answer["id"], answer["attempt_id"], answer["question_id"]))

async def start_sweep_loop():
    await sweep_stuck_jobs()   # 起動直後に1回実行
    while True:
        await asyncio.sleep(SWEEP_INTERVAL.total_seconds())
        await sweep_stuck_jobs()

    sweep_task.cancel()
    await database.disconnect()
再実行の重複起動に対する耐性: スイープが再スケジュールしたジョブと、たまたま同時に処理が続行していた元のジョブが両方完了すると、同じ行へ2回UPDATEが走る可能性がある。内容カラムへの書き込みはUPDATE ... WHERE id = ? AND (対応する内容カラム) IS NULLという条件を必ず付けることで、後勝ちではなく先着1回のみ反映させ、2重実行によるAPIコストの記録漏れ・不整合を防ぐ（2回目のUPDATEは0件更新で終わるが、T-19へのログ記録自体は2回分行われうる点は許容する。学習記録の欠落より二重課金の可能性の方が実害が小さいため）。

8.5 AI利用ログ・コスト計算

ai_client.pyは呼び出し完了時（成功・失敗いずれも）にT-19へ1行記録する。

# 単価表（USD / 1Mトークン）。Anthropicの公開単価改定時に更新する。
# 下表の数値はプレースホルダであり、実装時にAnthropic公式の最新料金表で確認・置き換えること。
MODEL_COSTS = {
    "claude-sonnet-5": {"input": 3.00, "output": 15.00},
    "claude-opus-5":   {"input": 15.00, "output": 75.00},
    "claude-haiku-4-5": {"input": 0.80, "output": 4.00},
}
USD_TO_JPY = 150  # 固定レート。概算表示のための定数（Keirekiと同方針）

def estimate_cost_jpy(model: str, input_tokens: int, output_tokens: int) -> float:
    costs = MODEL_COSTS.get(model, MODEL_COSTS[DEFAULT_MODEL])  # 未知モデルは既定モデル単価で概算
    usd = (input_tokens * costs["input"] + output_tokens * costs["output"]) / 1_000_000
    return round(usd * USD_TO_JPY, 6)

8.7 ai_client.py 共通呼び出し設計

  • 構造化出力: F-08・F-21はツール呼び出しで構造化JSONを受け取り、パース失敗時のフォールバック処理は挟まない（Claude APIのtool useは指定スキーマへの準拠が保証されるため）。F-20は同様にツール呼び出しを用いる。F-22・F-23は自由記述テキストで受け取る。
  • タイムアウト・リトライ: 1回の呼び出しにつきタイムアウト60秒、指数バックオフで最大3回リトライする（8.2節）。
  • モデル解決・ログ記録: 8.4節のモデル解決、8.5節のT-19記録はai_client.py内で一元的に行い、各機能の呼び出し元（materials.py, learning.py, dashboard.py, reports.py）はモデル名やログ記録を意識しない。
  • 例外処理: Claude API呼び出しの例外はlogger.exceptionでサーバーログに記録し、利用者にはAPIキーやエラー詳細を含まない汎用メッセージのみ返す（同期呼び出しのF-08は502、非同期呼び出しは8.2節のとおり内容カラムをNULLのまま残す）。

9.1 エラーレスポンス形式

全APIのエラーは{"detail": "メッセージ"}に統一する（LCC CRM・Keireki踏襲）。FastAPIのHTTPException標準形式のため、ハンドラはraise HTTPException(status_code, detail="...")のみを使用する。detailは利用者向けの日本語メッセージとし、スタックトレース等の内部情報は含めない。未捕捉例外は汎用ハンドラで500 {"detail": "サーバーエラーが発生しました"}に変換し、詳細はサーバーログにのみ出力する。

9.2 フロントエンドのエラー表示方針

  • データ取得系（SWR）: フックのerrorを各画面でハンドリングし、インラインのエラーメッセージ（再読込ボタン付き）を表示する。401はAPIクライアント共通処理で/loginへリダイレクトする
  • 更新系（保存・削除・招待応答等）: レスポンスのdetailをトーストで表示する（成功時は「保存しました」等の成功トースト）。detailが取得できない場合は汎用メッセージ「エラーが発生しました」を表示する
  • 403: 「この操作を行う権限がありません」をトースト表示する（画面遷移はしない）
  • AI非同期ジョブの404（pending）: エラーとして扱わず「作成中です…」等の待機表示に用いる（8.2節）
  • 413: 「ファイルサイズが上限（{MAX_ATTACHMENT_SIZE_MB}MB）を超えています」を専用メッセージとして表示する（detailをそのまま出すのではなく画面側で整形する）

11. 処理シーケンス

11.1 初回ログイン〜「全社公開」プロジェクトへの自動参加（S-01 → S-02）

  1. 【ブラウザ】未認証で/にアクセス → App.tsxがA-04を呼ぶ → 401 → /login（S-01）へリダイレクト
  2. 【ブラウザ】「Googleでログイン」押下 → A-01へ遷移 → Google認証・同意 → A-02へコールバック
  3. 【backend/routers/auth.py】state照合 → トークン交換・IDトークン検証 → ドメイン検証 → T-01 usersをemail検索、未登録のためrole='member'で新規登録（4.1節）
  4. 【backend】同一トランザクションで、is_company_wide=trueのプロジェクトIDに対するT-04 project_memberships行をrole='editor', status='active', joined_at=now()で作成（4.1節・基本設計書5.25節）
  5. 【backend】JWT発行（token_type='session'）→ HttpOnly Cookieに設定 → 構造化ログevent=login（is_new=true）記録 → 302で/へ
  6. 【ブラウザ】App.tsxが再度A-04を呼び200を取得 → S-02（マイ学習）を表示。A-39を呼ぶが、まだ配信設定（assignments）が無いため一覧は空
  7. 【ブラウザ】サイドバーの「教材編集」メニューを押下 → S-13（プロジェクト選択）に「全社公開」カードが表示されていることを確認できる（editorとして自動参加済みのため）

11.2 教材新規作成〜Claude Codeでの往復編集（F-05, S-14 → S-05 → Claude Code）

  1. 【ブラウザ】S-14「＋新規教材を作成」押下 → A-16（project_id省略。「全社公開」が既定補完）→ 201、下書き教材IDを取得 → S-05へ遷移
  2. 【ブラウザ】S-05目次編集タブでタイトルのみ入力し「下書き保存」→ A-17でtitleを更新
  3. 【利用者端末】Claude CodeでManabi materials get {id}相当のCLIコマンドを実行 → CLIヘルパーが保存済みのCLIトークン（7.1節）でA-19（GET /source）を呼ぶ → フロントマター＋空の本文（目次未作成のためタイトルのみ）をtext/plainで取得
  4. 【利用者】ローカルでMarkdownファイルとして章・小見出し・ページ・問題を執筆（基本設計書8.3節のスキーマに従う）
  5. 【利用者端末】Manabi materials update {id}相当のコマンド → A-20（PUT /source）を実行
  6. 【backend/materials.py】require_material_editorで権限判定 → 7.2節の手順でパース → 7.3節の手順でトランザクション内にてmaterials更新・material_nodes全置換・questions全置換 → T-08へchanged_via='claude_code'で改訂履歴行を追加（7.4節）→ 200で新規採番済みのソーステキストを返す
  7. 【ブラウザ】S-05を再読み込みすると、目次編集タブに新しい章・ページ構成が反映されている（画面とClaude Codeが同一データを共有）
  8. 【ブラウザ】「AIレビュー結果」タブでA-32を実行 → 同期でClaude APIを呼び出し（8.6節F-08）→ 指摘事項一覧を表示
  9. 【ブラウザ】指摘を踏まえて「公開する」押下 → A-17でstatus='published'に更新

11.3 受講〜記述式AI採点〜合否確定（S-04 → S-16 → S-04）

  1. 【ブラウザ】S-02から教材を選びS-04（目次）へ → A-15で目次取得、A-40（mode='graded'）で新規試行を開始
  2. 【ブラウザ】目次からページを選択 → S-16へ遷移。説明文閲覧後、選択式設問に回答するたびA-41で保存
  3. 【ブラウザ】記述式設問に回答し「回答して次のページへ」（最終ページ）→ A-42（提出）を呼ぶ
  4. 【backend/learning.py】選択式設問は即時採点。記述式設問は当該設問のgrading_modeが'ai'のためAI採点ジョブを非同期起動（8.2節）→ プレースホルダとしてanswers.ai_score_pct=NULLのまま200を返す（score_pct・passedは「採点中」を示すNULL）
  5. 【backend/8.2節ジョブ】ai_client.pyがClaude APIへ回答内容・採点基準を送信 → 構造化出力を受け取りanswers.is_correct, ai_score_pct, ai_feedbackを更新 → T-19へ利用ログを記録 → 4.5節A-42と同じロジックでquiz_attempts.score_pct, passedを再計算し確定
  6. 【ブラウザ】S-04に戻り、SWRのポーリングで採点結果が反映されたことを確認（3秒間隔でA-43を再検証）。ドボン問題があればfail_reasonを表示
  7. 【ブラウザ】不合格かつretake_allowed=trueの場合、「再受験する」ボタンを表示 → A-71（retake_scopeに応じて全問または誤答のみを含む新規試行を開始）
