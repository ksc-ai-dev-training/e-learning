1. 要件・制約

要求仕様書・要件定義書の該当箇所を確認した内容：

REQ-F-08必修教材の期限を設定し、未受講者を把握・催促できること。「対象者本人へSlackで受講を促せること」
F-11受講期限・未受講者管理。管理者・プロジェクト管理者が未受講者を一覧で把握できる
F-12Slack受講催促通知。未受講者へ、Slackで受講を促す通知を送る
制約条件利用者への通知はSlackとし、メールによる通知は行わない（誤送信時の影響が大きいため）
「本人へ」という文言は、非公開（DM限定）とまでは明記されていない。ただし「未受講である」という内容を第三者に見える形（プロジェクトの共有チャンネル等）で名指しするのは、本来の「個人への配慮ある催促」の意図から外れる可能性が高いと判断している（4章参照）。

2. 現在の実装状況

2026-09-03時点で、以下をコードとして実装済み（backend/routers/slack.py・slack_oauth.py・slack_client.py、フロントエンドS-15プロフィール編集・S-12メンバー管理）。

  • 本人がS-15「プロフィール編集」で一度だけSlack OAuth連携（chat:write・identity.basicのUser Token Scopesのみ、Bot User不使用）
  • 連携すると本人のUser Access Tokenを保存し、以後はそのトークンで本人宛てにDM送信
  • S-12メンバー管理から、プロジェクトadmin/システムadminが対象者の未受講必修教材を確認し、Slackでリマインドを送信

この方式（個別OAuth連携）は本人だけへの非公開DMを実現でき、要件の意図に最も忠実だが、後述の理由で現状は利用できない。

3. 直面している問題（Slackアプリ数の上限）

実際にSlackアプリを新規作成しようとしたところ、御社のSlackワークスペース（無料プラン）でインストール済みカスタムアプリ数が上限に達しており、新規アプリを作成できないことが判明した。

個別OAuth連携・Bot＋メール検索方式のどちらも、実現には新規Slackアプリが最低1個必要。方式（Bot方式かUser Token方式か）によってアプリ枠の消費数は変わらない。つまり「アプリの種類を変える」ことでは回避できない。

5. 各方式の詳細

A. 個別OAuth連携（実装済み）

本人がS-15で「Slack連携する」を押し、Slack側の認可画面でchat:write（User Token Scope）を許可する。以後、Manabiは本人のUser Access Tokenを使い、本人とのDMチャンネル（conversations.open）へchat.postMessageで投稿する。Bot Userを一切使わない。要件の「本人へ・非公開」を最も忠実に満たすが、新規Slackアプリが1個必要。

B. Bot＋メールアドレス検索

共有のBot Token（chat:write・users:read.emailのBot Token Scope）を持つSlackアプリを1個作成する。送信時に対象者のメールアドレスでusers.lookupByEmailを呼びSlackユーザーIDを特定し、Botとして本人へDMを送る。本人ごとのOAuth操作が不要になる分、利用者の手間は減るが、アプリが1個必要な点はAと同じ。

C. プロジェクトごとのIncoming Webhook

1つのSlackアプリで「Incoming Webhooks」機能を有効化すると、チャンネルを指定して複数のWebhook URLを発行できる（1チャンネル1URL）。プロジェクトごとに専用チャンネルを用意し、そのURLをManabi側でプロジェクトに紐づけて保存すれば、アプリは1個のままプロジェクトの数だけ送信先を持てる。ただし投稿はチャンネル向けであり、対象者以外にも内容が見える。メッセージ本文で対象者を名指し（メンション）すれば本人への通知（Slack上の個人宛て通知バッジ）は発生するが、「非公開」ではない。

D. Slack Workflow Builder

Slack標準のノーコード自動化機能。プランによってはWebhookで外部からトリガーできるワークフローを作成できる。ワークフロー内で特定の相手にDMを送るステップを組める可能性があるが、（1）Webhookトリガーが現行プランで使えるか、（2）外部から動的に「誰に送るか」を指定できるか、の2点が未確認。Slack標準機能のためアプリ数の上限に影響しないと考えられる点が利点。

E. 既存アプリの削除・流用

ワークスペースの「アプリ管理」に表示されている、御社が独自に作成・設定変更できるアプリがあれば、それを削除して枠を空ける、あるいはそのアプリに直接OAuthスコープを追加してA/Bの実装先として流用する。外部の既製アプリ（公式のGoogle Drive連携等）は設定変更・削除の対象にならない。
