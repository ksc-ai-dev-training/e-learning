本書は、社内学習管理システム（e-learning）の基本設計書である。要件定義書（v1.4）要件定義書（v1.5）で定義された要求事項（REQ-F-01〜REQ-F-19、REQ-N-01〜REQ-N-06）を実現するためのシステム構成・認証認可方式・画面・機能・データベース・API・教材連携・AI連携の設計方針を定める。実装レベルの詳細（カラム単位の入出力仕様、リクエスト/レスポンスのフィールド定義、バリデーション規則、フロントマターの完全な文法など）は後続の詳細設計書で定義する。

本システムは、社員経歴書管理システム「Keireki」と同じ研修シリーズの一部であり、デザインシステム・ドキュメント形式・ID体系（REQ-xx=要求 / F-xx=機能 / S-xx=画面 / T-xx=テーブル / A-xx=API）・技術スタックの多くをKeirekiから踏襲する。画面の詳細レイアウトは、実際に作り込まれた画面モックアップ「03_画面モックアップ/」を参照する。

教材作成者（author）ロールの権限論点について（v1.4で解消、v1.5でロール自体を統合）: 「author ロールが受講者（learner）と権限的にほぼ同一で、実質的な追加権限が何かという設計論点」は、v1.0執筆時点ではユーザーとの議論が保留中だった。要件定義書v1.4が導入したプロジェクトのローカルロール（管理者/編集者/受講者。F-24、要件定義書7.3節）により、教材の編集権限はオーナー・共同編集者ではなくプロジェクトのローカルロールで判定される割合が大きくなり、システム全体の「教材作成者（author）」ロールは編集権限の判定に用いられなくなった。要件定義書v1.5は、この経緯を踏まえて受講者(learner)・教材作成者(author)・部署長/PM(manager)の3ロールを廃止し、システム全体のロールをmember（一般ユーザー）／adminの2種に統合した（要件定義書7章）。あわせて教材は必ずいずれかのプロジェクトに属する方式に一本化され、個人所有の教材（オーナー・共同編集者モデル）も廃止された。本論点は、ロールと個人教材モデルの両方が整理されたことで完全に解消された。本書もこれに合わせてロール名称をmember/adminに更新し、3.4節（オーナー・共同編集者による認可）を廃止して設計している。詳細は3.3節・3.5節を参照。

3. 認証・認可設計

3.1 Google OAuth 2.0 認証フロー（F-01）

認証はGoogle OAuth 2.0（認可コードフロー）による。基本的な流れはKeirekiと同一である。

  1. 未認証ユーザーが S-01（ログイン画面）で「Googleでログイン」を押下すると、ブラウザは A-01 GET /api/auth/login にアクセスする。
  2. バックエンドは state を生成し、Google の OAuth 認可URLへリダイレクトする。
  3. ユーザーがGoogleアカウントで認証・同意すると、Googleは認可コード付きで A-02 GET /api/auth/callback にリダイレクトする。
  4. バックエンドは認可コードをアクセストークン・IDトークンに交換し、ユーザーのメールアドレス・氏名・プロフィール画像を取得する。
  5. メールアドレスのドメインを ALLOWED_DOMAINS（既定: kogasoftware.com）と照合する。許可ドメイン外は認証を拒否する（REQ-N-01）。
  6. T-01 users をメールアドレスで検索する。未登録なら role='learner'role='member' で自動登録する（初回ログイン）。この初回登録時のみ、Googleプロフィールの氏名をnameの初期値として設定する。登録済みで is_active=false の場合はログインを拒否する。登録済みユーザーの再ログイン時はnameを更新しない（S-15で本人が変更した表示名を、Googleアカウント側の氏名変更で意図せず上書きしないため。3.1節末尾のcallout・4.14a節参照）。
  7. ユーザーID・ロールを含むセッションJWTを発行し、HttpOnly Cookie にセットして / へリダイレクトする。
  8. SPAは起動時に A-04 GET /api/auth/me でログイン中ユーザー情報（id, email, name, role, picture_url, department_id）を取得し、ロールに応じた画面制御を行う。部署（department）の概念はv1.5でシステムから廃止したため、department_idは含まない。picture_urlは、T-01 custom_picture_keyが設定されていればそのアイコン画像の署名付きURL、未設定であればGoogleプロフィール画像のURLを返す（4.14a節）。
  9. ログアウトは A-03 POST /api/auth/logout でセッションCookieを破棄する。
表示名の同期タイミングを「初回登録時のみ」とした理由（v1.22）: 当初はKeirekiと同様に「既存ユーザーもログインのたびにGoogleプロフィールの氏名・画像で上書きする」運用を想定していたが、S-15（プロフィール編集）で表示名を自己編集できる機能を新設したことに伴い、この運用のままでは本人が変更した表示名が次回ログイン時にGoogle側の氏名で意図せず上書きされてしまうという欠陥が生じる。これは「氏名を変更したはずなのに、ログインし直すと元に戻る」という体験になり、自己編集機能そのものを無意味にする。そこでnameは初回登録時（Googleプロフィールの氏名を初期値として使う場面）にのみ設定し、以降の再ログインでは更新しない方式に改めた。Googleアカウント側で氏名を変更した場合でも、本システムの表示名は本人がS-15で明示的に変更するまで変わらない。picture_url（Googleプロフィール画像）は逆に「独自アイコン未設定の場合のフォールバック」として毎回参照する値であるため、こちらは引き続き常に最新のGoogle側の値を返す（値をDBにコピー・キャッシュしない）。

3.4 教材ごとのオーナー・共同編集者による追加の認可レイヤー

廃止（v1.5）: 要件定義書v1.5で教材は必ずいずれかのプロジェクトに属する方式に一本化され、個人所有の教材（materials.project_id が NULL の教材）とそれに伴うオーナー・共同編集者モデルは廃止された。本節が定めていた「教材1件ごとの行レベル認可」（require_material_editor の判定ロジック）、およびそれが行っていたproject_id の有無による3.4節/3.5節の分岐は不要になった。教材編集権限の判定は、常に3.5節のプロジェクトのローカルロール（管理者/編集者）による判定のみで行う。require_material_editor(material_id, user) 依存関数は3.5節の require_project_role を呼び出すだけの薄いラッパーとして残すか、呼び出し元を require_project_role に直接置き換えるかは詳細設計で定める。T-07 material_co_editors テーブルは廃止し、T-06 materials.owner_id は編集権限判定には用いず、作成者を記録するだけの created_by に読み替える（6章参照）。共同編集者の追加・削除・オーナー引き継ぎという操作自体も、プロジェクトのメンバー管理（S-12、3.5節）に置き換わったため廃止する。旧仕様（オーナー・共同編集者モデル、個人教材の扱い）の設計判断の詳細は、本改訂前のリビジョン（v1.1）を参照のこと。

3.5 プロジェクトのローカルロールによる認可

要件定義書7.3節が定める「プロジェクトのローカルロール」は、3.3節のシステム全体ロール（learner/author/manager/adminmember/admin）とは独立した、プロジェクト1件ごとの認可レイヤーである。教材は必ずいずれかのプロジェクトに属するため（F-25）、教材編集権限の判定は本節のロジックのみで行い、3.4節（廃止）が定めていたオーナー・共同編集者モデルとの分岐は存在しない。プロジェクトは誰でも新規作成でき（F-24）、作成時に T-04 project_memberships へ作成者を role='admin', status='active' で自動登録する。以降のメンバーの追加招待・削除・ロール変更は、そのプロジェクトの管理者のみが行える（社員本人による自己申告は行わない）。ただしメンバーの追加は招待制であり、招待された本人が承諾するまでは実際の権限を持たない（詳細は本節末尾のcallout参照）。

  • 招待への応答: 招待された本人が新設API A-67（PUT /api/project-memberships/{id}/respond）で承諾（status='active'、joined_at=now()）または辞退（status='declined'）する。この操作は招待された本人のみが行え、プロジェクト管理者は代行できない。承諾・辞退の一覧・応答はS-15（プロフィール編集）の「招待されているプロジェクト」セクションで行う。
  • 教材編集権限判定: require_material_editor(material_id, user)（3.4節）は、対象教材の materials.project_id を確認し、NULL なら3.4節の判定（オーナー・共同編集者）、非NULLなら本節の require_project_role(project_id, user, min_role='editor') に処理を委譲する。require_material_editor(material_id, user) は、対象教材の materials.project_id（教材は必ずいずれかのプロジェクトに属するためNOT NULL。6章参照）に対して本節の require_project_role(project_id, user, min_role='editor') を呼び出すだけの処理となる。3.4節は廃止したため、個人教材（project_id IS NULL）向けの分岐は存在せず、教材編集権限の判定は常に本節のロジックのみで行う。教材の受講可否（配信対象、F-09）とは別の判定である点に注意する。詳細は5.26節（F-25）参照。
なぜプロジェクト単位のローカルロールを導入したか: v1.3までの「オーナー・共同編集者」モデルは、プロジェクト単位で配信される教材でもオーナー個人に紐づくため、オーナーの異動・離任のたびに引き継ぎ操作が必要だった（3.4節）。v1.4はこれに加え、プロジェクトという単位そのものにロール（管理者/編集者/受講者）を持たせることで、「誰が管理者か」「誰が編集できるか」をプロジェクト側で一元管理できるようにした。またプロジェクトの新規登録をadmin限定から誰でも可能にしたことで、旧v1.3の「プロジェクト所属の自己申告制」（3.3節の権限マトリクスにあった行）は不要になった。メンバーの追加・削除・ロール設定という能動的な操作をプロジェクト管理者に一本化したためである。
なぜメンバーの追加を招待制にしたか: 誰でもプロジェクトを新規作成できる方式（F-24）のもとで、当初は「プロジェクト管理者がメンバーを追加すれば即座に有効」という設計だった。しかしこれでは、管理者が本人の同意なしに一方的に他の社員をメンバーへ追加でき、追加された側は気づかないうちに教材の受講対象に加わり、管理者/編集者ロールで追加されれば編集権限まで持たされてしまう（5.27節のF-26で対応した「教材共有の一方的な押し付け」と同じ構造の欠陥）。そこでT-04 project_memberships に status（'invited'/'active'/'declined'）を追加し、追加は「招待」として status='invited' で作成するだけに留め、本人が承諾するまで require_project_role の判定を通さない（=いかなる権限も持たない）ようにした。プロジェクト作成者自身と「全社公開」への自動参加（いずれも本人の意思や全社的な合意に基づく）だけは、この性質上招待を経ず status='active' で作成する。

設計判断（全社スコープをrequiredで権限分岐する理由）: 要件定義書v1.5でF-25（プロジェクト単位教材管理）に一本化されたことで、社員が「気軽に社内へ共有する」（REQ-F-04）ための唯一の経路は、自分のプロジェクトで教材を作り、それを他の人にも見えるようにすることになった。ここで全社スコープの作成を一律adminに限定すると、必修教材の配信（重要な運用で一元管理すべき）だけでなく、単なる任意共有までadminのボトルネックを経由することになり、REQ-F-04の趣旨に反する。そこで新しいscope_typeを追加するのではなく、既存のrequiredフラグで権限を分岐させる: scope_type='company'かつrequired=trueの行の作成・更新は管理者専用のAPI権限判定（3.3節のadmin判定）とし、required=falseの行は対象教材のプロジェクトの管理者判定（require_project_role(project_id, user, min_role='admin')、3.5節）でも許可する。既存のscope_type列挙値・テーブル構造を変えずに、最小限の権限判定の分岐だけで実現できる。
設計判断（複数スコープはOR結合）: 画面モックアップ（S-06）は「部署Xかつ特定プロジェクトAかつ別のプロジェクトを組み合わせて指定できる」という複合条件のUIを示しているが、要求定義書は複数単位を「組み合わせて指定できる」とのみ規定し、AND/ORいずれで結合するかまでは規定していない。本書では実装をシンプルに保つため、1教材に対して複数の T-11 assignments 行（scope_type×scope_idの組み合わせ数分）を持たせ、行間はOR結合（いずれかの条件に合致すれば対象者）とする。真に「部署Xの中でもプロジェクトYのメンバーのみプロジェクトXのメンバーのうちプロジェクトYのメンバーでもある者のみ」というAND条件が必要な場合は、対象者を個人（individual）スコープとして展開して登録する運用とし、AND専用のスコープ種別は設けない。合否判定・再受験の条件（pass_score_pct・retake_allowed・retake_limit）は教材単位で1つに定める運用とし、複数スコープを設定する場合も同一教材内では同じ値を複製して保持する。これらの値は配信設定（S-06、scopeごとの設定画面）ではなく、教材の作成者が決める性質の値であるため、S-05「合否判定・再受験設定」・A-17（教材メタデータ更新）から入力し、対象教材の全T-11行へ同一値を書き込む（7.2.3節A-17参照。v1.22で実施主体を明記）。

5.20 F-20 AI記述式採点・講評

処理概要: 記述式回答をAIが採点し、根拠を伴う講評を返す。採点結果は人が確認・修正できる（対応要求: REQ-F-16）。処理方式（非同期ジョブ）は9章参照。採点結果（ai_score_pct・ai_feedback）は T-14 answers に保存し、教材のオーナー・共同編集者対象教材が紐づくプロジェクトの管理者・編集者が reviewed_by・reviewed_at を設定して修正できる（S-19、v1.17）。

AI講評スタイル（v1.17）: 設問のfeedback_style（未設定時はmaterials.default_feedback_style）に応じてプロンプトの指示を切り替える。show_answer（模範解答＋講評を提示。既定）、review_only（正解は提示せず、コード記述式なら問題箇所の指摘のみ）、hint_only（正解を見せず、考え方のヒントのみ）。materials.ai_context（言語・フレームワーク・「正解を直接教えない」等の教材共通の前提）が設定されている場合は、これもプロンプトに追加する。

コード記述式問題（type='code'）の採点: 提出されたコード（T-14 response）・出題の模範解答/採点基準（T-10 scoring_criteria）・言語ヒント（code_language）をプロンプトに含め、Claude APIにコードを実行せず読解させ、想定される実行結果・エラーの有無を推論して正誤を判定させる。ai_feedbackには正誤の判定根拠に加え、無駄な処理の簡略化など改善提案があれば含めるよう構造化出力のスキーマに項目を設ける（例: {"correct": bool, "reasoning": str, "improvement_suggestions": str | null}）。

なぜコードを実行せず読解のみで採点するか: 提出されたコードを実際に実行するには、任意のコードを安全に動かせるサンドボックス実行環境（コンテナ分離・リソース制限・ネットワーク遮断等）が必要になり、2章で定めたUvicorn単一プロセス構成には収まらない、独立したインフラの新設を要する。要件定義書3.1節・3.2節は、対象を教育用の簡単な課題（数式処理・辞書操作等）に絞ることでAIの静的読解による採点を許容し、コード実行環境は初期実装の対象外としている。本設計もこれに従い、Claude APIへのコード読解のみで採点を行う。ループの繰り返し回数が多い・数値計算が精密といった、AIの読解精度が下がりやすい課題を出題する場合は、教材編集者が採点結果を確認・修正する運用（REQ-F-16）を徹底する。

手動採点（grading_mode='manual'、v1.18）: 記述式・コード記述式の設問は、教材既定（materials.grading_mode）または設問ごとの上書き（questions.grading_mode）で「AI自動採点」の代わりに「対象教材が紐づくプロジェクトの管理者・編集者による手動採点」を選べる。この場合、回答提出時にAI採点ジョブは実行されず、answers.is_correct・ai_score_pct・ai_feedbackはNULLのまま（S-19では「未採点」表示）となる。プロジェクト管理者・編集者がS-19で内容を読んで正誤・講評を入力するとreviewed_by・reviewed_atが設定され、ai_feedbackにはAIではなく担当者が入力した講評テキストが保持される。合否判定（F-14）・つまずき分析（F-21）は採点結果の由来（AI/人）を区別せず、確定したis_correctのみを見るため、既存のロジックへの影響はない。feedback_style（AI講評スタイル）は手動採点の設問には適用されない（AIが講評を生成しないため）。

5.25 F-24 プロジェクト管理

処理概要: プロジェクトは誰でも新規作成でき（対応要求: REQ-F-06）、作成者は自動的にそのプロジェクトの管理者（ローカルロール、3.5節）になる。プロジェクト情報（名称・説明・状態）の編集、メンバーの追加招待・削除、メンバーのロール（管理者/編集者/受講者）の設定は、そのプロジェクトの管理者が行う。メンバーの追加は招待制であり（A-12）、招待された本人がA-67で承諾するまでは status='invited' のままで実際の権限を持たない。詳細は3.5節を参照。運用上は部署長・PMがプロジェクトを作成して管理者となることを想定するが、システムとして作成者を限定しない。

「全社公開」プロジェクト: システムは初期データとして、削除不可の特別プロジェクト「全社公開」（is_company_wide=true、6章参照）を1行だけ保持する。新規ユーザーはA-02（初回ログイン）の処理内で、このプロジェクトへ自動的にrole='editor'として登録される（assigned_byはNULL、システムによる自動付与）。このプロジェクトの管理者（role='admin'）はシステム管理者のみとし、通常のプロジェクト作成フロー（A-09）やメンバー管理API（A-12/A-13）では新たに作成・変更できない。用途は5.26節（F-25）を参照。

猶予期間の実現: プロジェクト管理者によるメンバー管理は、v1.3までの自己申告制と異なり、本人以外の操作で急にアクセスを失いうる。管理者による設定の反映が遅れたり対応が漏れたりする場合に備え、メンバーがプロジェクトから削除された場合は、T-21 app_settings（key='project_leave_grace_period_days'、既定30日、S-10で変更可）で定めた猶予期間中、旧プロジェクト単位で配信された教材への閲覧アクセスを継続する。判定は「現役メンバー（T-04 project_memberships.status='active' AND left_at IS NULL。招待中〔status='invited'〕のメンバーは現役に含めない）」または「left_at + 猶予日数 >= 現在時刻」のいずれかを満たすかで行い、F-09（配信対象設定）のアクセス可否判定に組み込む（v1.3の「離任（自己申告）」を「削除（管理者操作）」に読み替えた以外は、5.3節旧版の判定ロジックを踏襲する）。

設計判断（ロール降格時は猶予期間の対象外とする）: S-12モックアップの注記は「メンバーを削除、またはロールを『受講者』以外から変更した場合も、猶予期間中は旧プロジェクトの教材への閲覧アクセスを継続する」としている。しかし本設計では、プロジェクトに残ったままロールが編集者/管理者から受講者へ降格された場合は、受講者ロールが引き続き該当教材の受講権限を持つため、閲覧アクセスが途切れることはない。したがって猶予期間の判定対象は「プロジェクトから削除された（メンバーでなくなった）場合」のみとし、ロール降格それ自体では猶予期間を発生させない設計とした。降格に伴う編集権限の喪失は即時反映とする（誤操作による情報流出リスクを避けるため）。

5.27 F-26 教材のプロジェクト間共有

処理概要: プロジェクトに紐づく教材を、別のプロジェクトでも受講・参照できるよう共有できる（対応要求: REQ-F-06）。共有の申請権限は、教材が紐づく元プロジェクトの管理者が持つ（require_project_role(materials.project_id, user, min_role='admin')）。共有はT-22 material_project_shares に行を追加することで表現し、共有先プロジェクトのメンバーは当該教材を受講対象として扱う（編集権限は共有によって移動せず、常に元プロジェクトの管理者・編集者が持つ）。申請するとT-22 material_project_shares に status='pending' の行が追加されるだけで、この時点では共有先プロジェクトの受講対象には反映されない。共有先プロジェクトの管理者（require_project_role(shared_to_project_id, user, min_role='admin')）が承認（status='accepted'）して初めて、共有先プロジェクトのメンバーが当該教材を受講対象として扱う。却下（status='rejected'）した場合は反映されない。承認・却下いずれの場合も編集権限は共有によって移動せず、常に元プロジェクトの管理者・編集者が持つ。承認待ち・承認済みいずれの共有も、共有元・共有先どちらのプロジェクト管理者からも解除できる。下書き（status='draft'）の教材は共有申請できない。

6.3 共通設計方針

  • 主キー: id は BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY で統一する（T-21のみ key TEXT を主キーとする、Keirekiと同方針）。
  • タイムスタンプ: created_at / updated_at は TIMESTAMPTZ NOT NULL DEFAULT now() で全テーブルに付与する。
  • コード値（role, format, status, mode, type, kind, scope_type）はCHECK制約で許容値を担保する。
  • JSONB項目（options, correct_answer, response, question_order, findings, weak_questions等）は、詳細設計書でスキーマ（フィールド定義）を定める。
  • スキーマ定義は backend/database.py（SCHEMA定義）に集約し、テーブル定義書を docs/ で管理する。

各テーブルのカラム詳細（型・NULL可否・制約・既定値の全定義）は詳細設計書に委ねる。

RLS方針: 全テーブルでRow Level Security（RLS）を有効にする（ALTER TABLE ... ENABLE ROW LEVEL SECURITY;）。アプリケーションは asyncpg で直接接続するため通常アクセスの権限判定（3章のRBAC・オーナー/共同編集者判定プロジェクトのローカルロール判定）はAPI層で行うが、Supabaseの他経路（PostgREST等）からの意図しない参照を遮断する多層防御として全テーブルRLSを必須とする（Keirekiと同方針）。

7. API設計

7.1 API設計方針

ベースパスは /api とする。認証はセッションJWTとし、ブラウザからのリクエストはHttpOnly Cookie（3.2節）、Claude Code等のCLIクライアントからのリクエストは Authorization: Bearer <token> ヘッダーで送信する（トークンの発行方式は8.2節）。A-01・A-02・A-62（いずれもログイン開始系のエンドポイント）を除く全APIで認証を必須とする。レスポンス形式はJSONを基本とし、教材テキストの往復系API（A-19〜A-21）のみ text/plain; charset=utf-8 を用いる（8.4節）。エラー形式はlcc_crm・Keirekiを踏襲し {"detail": "メッセージ"} とする。権限不足は403、対象なしは404、業務ルール違反（唯一の管理者の削除・降格等）は400、入力形式不正はFastAPI既定の422を返す。権限判定は全てサーバー側（auth_helpers.py の権限デコレーター・依存関数）で行い、下表の「権限」列は3.3節（システム全体ロール）・3.5節（プロジェクトのローカルロール）の判定ロジックに沿って表記する（凡例は7.3節）。

8.5 改訂履歴（T-08 material_revisions）の記録方式

本文または問題を変更するAPI（A-20、A-31）の呼び出しが成功するたびに、T-08へ1行追加する。メタデータのみを変更するA-17（タイトル・状態・所属変更等）はT-08の対象とせず、10.4節の構造化監査ログで別途記録する。

  • body_snapshot・format: 変更後のmaterials.body・materials.formatの全文スナップショット（差分ではなく毎回全文を保存する。差分計算はA-22の一覧表示側で行う）。
  • changed_by: リクエストのJWTから取得したユーザーID。
  • changed_via: JWTペイロードのtoken_typeクレームで機械的に判定する。token_type='session'（ブラウザCookie経由）なら'web'、token_type='cli'（8.2節のCLIトークン経由）なら'claude_code'とする。S-05のMarkdown/HTMLエディタタブもA-19/A-20を呼び出すが、ブラウザ経由であればchanged_via='web'として記録され、Claude Code経由の変更と区別できる。
  • change_summary: A-20呼び出し時にフロントマターまたはリクエストヘッダーで明示的な要約（例: Gitのコミットメッセージに相当するもの）が渡されればそれを使用し、渡されなければ「本文を更新」「問題をN件追加/M件更新」のように変更内容から自動生成する。A-31（画面からの問題一括更新）は常に「問題を更新（画面操作）」とする。

8.6 HTMLサニタイズの実現方式

要件定義書5.1節が定める「許可リスト方式でサニタイズする」方針を、以下のとおり実装レベルで具体化する。

  • ライブラリ: Python製の nh3（RustのAmmoniaライブラリのバインディング。許可リスト方式で高速・保守が活発）を採用する。旧来のbleachは開発が停滞しているため採用しない。
  • サニタイズのタイミング（提供時のみ、原文は変更しない）: materials.bodymaterial_nodes.body（v1.11でmaterials.bodyから移管）・T-08のbody_snapshotには、著者（Web画面またはClaude Code）が入力した原文をそのまま保存する。サニタイズは、教材を閲覧させる（レンダリングする）境界すべてで、都度実行する。具体的には (1) 受講者への提供時（A-15、A-40のレスポンス生成時、S-04S-16でのレンダリング直前）、(2) S-05本文編集タブのプレビュー表示時S-17ページ編集の説明文プレビュー表示時（A-64。保存前の未確定コンテンツであっても例外なくサニタイズを通す。他の編集者・管理者が同じ教材を開いたときの閲覧経路でもあるため、書き手自身の入力だからといって省略しない） の2箇所である。Markdown形式の教材はmarkdown_render.pyでHTMLへレンダリングした結果を、HTML形式の教材は原文そのものを、共通のhtml_sanitize.pyのサニタイズ関数に通してから返す。この際、本文中の問題ブロック（8.3節）はサニタイズ対象の本文から取り除き、対応するT-10のレコードに基づく問題カード（構造化UI）として別途表示する。フロントエンドはmaterials.bodyや編集中の生テキストをdangerouslySetInnerHTML等で直接描画してはならず、必ずA-15/A-40/A-64のいずれかが返すサニタイズ済みHTMLのみを描画する。
  • 許可タグ: p, br, strong, em, u, s, code, pre, blockquote, ul, ol, li, h3, h4, h5, h6, table, thead, tbody, tr, th, td, a, img, figure, figcaption。h1・h2・h3は許可しない（h2は5.4節で単元境界として予約済みであり、本文レンダリング後のHTMLでは単元見出し自体を別UIコンポーネントとして描画するため、本文内に残った生のh2は不要かつ構造を壊すh1/h2/h3は8.3節で章・小見出し・ページの境界として予約済み。ページ本文（material_nodes.body）は該当ページ見出し直下のテキストだけを抽出して保存するため、本文内に生の見出しが残ることは想定しないが、防御的にレンダリング層でも除去する（v1.11））。
  • 許可属性: a[href, rel, target]（hrefはhttp:/https:スキームのみ許可しjavascript:等は除去。rel="noopener noreferrer"を強制付与）、img[src, alt, width, height]（srcはSupabase Storageの署名付きURLまたはhttps:のみ）、table系要素のcolspan/rowspan。それ以外の属性（style、class、on*イベントハンドラ等）はすべて除去する。

なぜ書き込み時ではなく提供時にサニタイズするか: REQ-F-02は「取得して修正し、戻せること（往復できること）」を要求している。書き込み時にサニタイズ・変換した結果を保存してしまうと、Claude Codeが取得（A-19）した内容が著者の入力そのものではなくなり、意図しない改変が往復のたびに蓄積しうる（例: プログラミング教材のコードブロック内に説明用の<script>タグの例が含まれる場合、書き込み時にこれを除去してしまうと元の教材内容が失われる）。そのため本設計では、保存された原文には一切手を加えず、受講者に見せる直前（提供時）にのみ都度サニタイズを適用する。これにより原文の往復忠実性（REQ-F-02）とXSS対策（要件定義書5.1節）を両立させる。

9.2 非同期ジョブの実現方式

2章のシステム構成図が示すとおり、本システムはKoyeb上でUvicorn 1プロセスとして稼働し、AIジョブも同一プロセス内で実行する。この制約と、想定規模（社員200名程度）を踏まえ、Redis・Celery等の別プロセスのジョブキュー基盤は導入せず、FastAPIの非同期処理機構のみで非同期ジョブを実現する。

  • 起動: A-42（提出）・A-34（つまずき分析）・A-48（組織レポート）・A-51（個人フィードバック）は、リクエストを受けたらまず結果テーブル（T-16〜T-18）にrequested_at=now()のプレースホルダ行を同期的に作成し（内容カラムはNULLのまま）、その後でAI呼び出しを asyncio.create_task（FastAPIのBackgroundTasks相当）でスケジュールし、即座に202相当のレスポンス（受付済みを示すJSON）を返す。Uvicornのイベントループ上でAI呼び出し（ネットワークI/O待ち）が進む間も、他のリクエスト処理はブロックされない。
  • ジョブ状態の表現（専用のジョブテーブルを持たない）: ジョブの進行状況は、対応する結果テーブル（T-14のai_score_pct／T-16 ai_material_insights／T-17 ai_personal_feedback／T-18 ai_org_reports）自体の状態で表現する。T-16〜T-18は該当機能の実行ごとに行が作成される設計のため、「対象の行が存在しない」＝処理中、「行が存在する」＝完了として扱う。T-16〜T-18は上記のとおりリクエスト受付時に行を作成するため、「内容カラムがNULL」＝処理中、「内容カラムが設定済み」＝完了として扱う。T-14（記述式採点）は既存行のai_score_pctがNULLのままであれば「採点中」である（5.14節ですでに定義済み）。
  • 取得（ポーリング）: フロントエンドはA-35/A-43/A-49/A-52をSWRの再検証間隔付きで呼び出し、結果が存在するまで数秒間隔でポーリングする。WebSocket等のプッシュ通知は本フェーズでは導入しない（想定規模・実装コストに見合わないため）。
  • 失敗時のリトライ: Claude API呼び出しが失敗した場合、ジョブ内で指数バックオフにより最大3回リトライする（要件定義書6.2節）。全て失敗した場合も当該行は削除せず内容カラムをNULLのまま残し（学習記録自体は失われない、REQ-N-05）、構造化ログ（10.4節）にエラーを記録する。フロントエンドは一定時間（目安3分）応答がない場合に「時間がかかっています」の案内を表示し、再試行操作（同一APIの再呼び出し）を可能にする。
  • プロセス再起動・デプロイによるジョブ消失への対策: asyncio.create_taskでスケジュールしたタスクはプロセスのメモリ上にのみ存在するため、Koyebのデプロイ（10.5節、mainマージ即時反映）やクラッシュでプロセスが再起動すると、実行中のタスクはリトライも記録も残らず消える。この場合でも上記のプレースホルダ行（requested_atあり・内容カラムNULL）は残るため、これを起点に検出・復旧する。具体的には、アプリ起動時（lifespanイベント）およびその後5分ごとに、requested_atが10分以上前かつ内容カラムがNULLの行（T-16〜T-18）と、submitted_atが10分以上前かつai_score_pctがNULLの回答（T-14）を検出し、AI呼び出しを再スケジュールする「スタックジョブ・スイープ」を実行する。これにより、途中で失われたジョブも次回のスイープで自動的に再試行され、受講者・教材編集者が結果を永久に待ち続ける状態を防ぐ。専用のジョブキュー基盤（Redis・Celery等）を導入しない9.2節の方針を維持したまま、想定規模（社員200名程度、デプロイ頻度は開発時のみ高い）に見合う最小限の復旧策とする。

9.3 AI利用ログ（T-19 ai_usage_logs）の記録方式

Claude APIの呼び出しは、必ず共通クライアント（ai_client.py）を経由させる。ai_client.pyは呼び出しの成否によらず、呼び出し完了時にT-19へ1行記録する。

  • feature: 呼び出し元機能を識別する固定値（material_review / grading / insight_analysis / personal_feedback / org_report / draft_assist（F-27、A-69。F-27はv1.20で廃止したため今後この値が記録されることはない））。
  • model: 実際に呼び出されたモデルID（9.4節の優先順位で解決された値）。
  • input_tokens・output_tokens: Messages APIのレスポンスに含まれるトークン数をそのまま記録する。
  • cost_estimate: input_tokens × 単価_in + output_tokens × 単価_outで概算する。モデルごとの単価はai_client.py内の定数テーブルとして保持し、Anthropicの価格改定時にはこの定数を更新する（本書では具体的な単価は定めない）。通貨は画面モックアップ（S-10）に合わせ円（JPY）で表示する。
  • 内容そのものは記録しない: 要件定義書6.2節・Keirekiのai_usage_logsと同方針で、プロンプト・レスポンスの本文は保存しない。
AI利用費用の管理方法（要件定義書9.2節「別途整理する」の対応）: S-10のシステム設定タブは、当月のトークン数・概算コストの表示（既に画面モックアップで確定済み）のみを持つ。本設計ではこれに加え、環境変数AI_MONTHLY_BUDGET_ALERT_JPY（任意設定、既定は未設定＝アラートなし）を導入する。ai_client.pyはAPI呼び出し完了時に当月のcost_estimate合計を集計し、閾値を超えた場合は10.4節の構造化ログに警告レベルで記録する。画面上の新たな設定項目を追加すると4章（画面設計）の確定済み内容に踏み込むため、本フェーズでは環境変数による運用者向けの目安機能に留め、S-10でのUI化（閾値入力欄・Slackアラート連携等）は将来の拡張として詳細設計以降で検討する。

記録対象ログイン（成功/失敗）、教材のメタデータ変更（A-17、状態変更含む）、配信設定の変更（A-38）、ユーザーのロール変更・有効/無効化（A-54）、プロジェクトメンバーの追加・削除・ロール変更（A-12, A-13）、AIジョブの失敗、AI月次コスト閾値超過（9.3節）を構造化ログに記録する。教材の本文・問題の変更はT-08 material_revisions（8.5節）で管理するため本ログの対象外とする
記録内容日時・操作ユーザー・操作種別・対象（material_id/user_id等）・結果。個人情報の本文値・回答内容そのものはログに残さない
出力先アプリケーションログとして標準出力へJSON形式で出力し、Koyebのログ基盤で参照する（Keirekiと同方針）

10.5 デプロイ

項目方針
ホスティングKoyeb。mainブランチ=本番 / stagingブランチ=ステージング（2.1節）
リリースフローstagingへマージ→ステージング環境で動作確認→mainへマージ→本番反映（Gitブランチ連動の自動デプロイ）
ビルドデプロイ時にフロントをvite buildでビルドし、FastAPIが静的配信する（2.3節参照）
環境分離環境変数（APP_ENVほか、2.3節）を環境ごとにKoyeb上で設定する。DB（Supabase）・Storage・AI/Slackの各キーも環境ごとに分離する
デプロイタイミング10.2節のとおり業務時間限定の前提を撤廃したため、「利用の少ない深夜・早朝にデプロイする」ことを前提にはできない。Koyebのローリング再起動（新プロセス起動後に旧プロセスを切替）により切替時の瞬断を最小化する。デプロイに伴う再起動で実行中の学習操作・AIジョブが中断されても、進捗・回答は都度DBへ保存済みであり（5.15節）、AIジョブはスタックジョブ・スイープ（9.2節）で自動的に再試行されるため、学習記録が失われることはない
