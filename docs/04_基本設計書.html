1. はじめに

1.1 本書の位置づけ

本書は、社内学習管理システム（e-learning）の基本設計書である。要求定義書（v1.3）で定義された要求事項（REQ-F-01〜REQ-F-19、REQ-N-01〜REQ-N-06）を実現するためのシステム構成・認証認可方式・画面・機能・データベース・API・教材連携・AI連携の設計方針を定める。実装レベルの詳細（カラム単位の入出力仕様、リクエスト/レスポンスのフィールド定義、バリデーション規則、フロントマターの完全な文法など）は後続の詳細設計書で定義する。

本システムは、社員経歴書管理システム「Keireki」と同じ研修シリーズの一部であり、デザインシステム・ドキュメント形式・ID体系（REQ-xx=要求 / F-xx=機能 / S-xx=画面 / T-xx=テーブル / A-xx=API）・技術スタックの多くをKeirekiから踏襲する。画面の詳細レイアウトは、実際に作り込まれた画面モックアップ「03_画面モックアップ/」を参照する。

教材作成者（author）ロールの権限論点について: 「author ロールが受講者（learner）と権限的にほぼ同一で、実質的な追加権限が何かという設計論点」は、本書執筆時点でユーザーとの議論が保留中である。本書では要求定義書v1.3に記載された現状の権限モデル（4ロール制＋教材ごとのオーナー・共同編集者による追加の認可レイヤー）をそのまま前提として設計しており、この論点を先取りして解決したり独自の結論を出したりはしていない。後日 author ロールの結論が出た場合、本書の3章・7.3節・権限マトリクスを別途改訂する。

2. システム構成

2.1 システム構成図

本システムは、React製SPAをフロントエンドとし、Koyeb上でホスティングするFastAPIがAPIを提供、データストアにSupabaseのPostgreSQLを用いる3層構成である。既存システムLCC CRM・Keirekiの構成を踏襲する（REQ-N-06）。これに加え、教材添付ファイルの保存にSupabase Storage、AI機能の実現にAnthropic Claude API、受講催促通知にSlack Incoming Webhookを利用する。

3. 認証・認可設計

3.1 Google OAuth 2.0 認証フロー（F-01）

認証はGoogle OAuth 2.0（認可コードフロー）による。基本的な流れはKeirekiと同一である。

  1. 未認証ユーザーが S-01（ログイン画面）で「Googleでログイン」を押下すると、ブラウザは A-01 GET /api/auth/login にアクセスする。
  2. バックエンドは state を生成し、Google の OAuth 認可URLへリダイレクトする。
  3. ユーザーがGoogleアカウントで認証・同意すると、Googleは認可コード付きで A-02 GET /api/auth/callback にリダイレクトする。
  4. バックエンドは認可コードをアクセストークン・IDトークンに交換し、ユーザーのメールアドレス・氏名・プロフィール画像を取得する。
  5. メールアドレスのドメインを ALLOWED_DOMAINS（既定: kogasoftware.com）と照合する。許可ドメイン外は認証を拒否する（REQ-N-01）。
  6. T-01 users をメールアドレスで検索する。未登録なら role='learner' で自動登録する（初回ログイン）。登録済みで is_active=false の場合はログインを拒否する。
  7. ユーザーID・ロールを含むセッションJWTを発行し、HttpOnly Cookie にセットして / へリダイレクトする。
  8. SPAは起動時に A-04 GET /api/auth/me でログイン中ユーザー情報（id, email, name, role, picture_url, department_id）を取得し、ロールに応じた画面制御を行う。
  9. ログアウトは A-03 POST /api/auth/logout でセッションCookieを破棄する。

3.4 教材ごとのオーナー・共同編集者による追加の認可レイヤー

要求定義書7章が定める「教材の改訂（オーナー・共同編集者）」は、3.3節のロールベース権限（RBAC）とは独立した、教材1件ごとの行レベル認可である。「受講者が自分で作成・共有した教材でも、オーナーであれば編集できる」（S-05の設計方針）を成立させるため、ロールでは判定できない。

  • 判定ロジック: auth_helpers.py に require_material_editor(material_id, user) 依存関数を設け、S-05（教材編集）・教材更新系API（7章 A-17, A-19〜A-31 等）すべてで共通利用する。判定は次の優先順で行う。
    1. user.role == 'admin' なら許可（保守目的の全教材編集権）
    2. materials.owner_id == user.id なら許可
    3. material_co_editors に (material_id, user.id) の行が存在すれば許可
    4. いずれにも該当しなければ 403
  • 共同編集者の追加・削除・オーナー引き継ぎ: オーナー本人または admin のみが行える（共同編集者自身は不可）。プロジェクト単位の教材はオーナーの異動・離任後も、admin または既存の共同編集者がオーナーを引き継げるようにするため、オーナー引き継ぎ操作は「オーナー本人 or admin」に限定する（共同編集者からの一方的なオーナー交代は認めない）。
  • RBACとの関係: ロール（learner/author/manager/admin）は「そもそも教材編集機能にアクセスできるか」を判定せず、S-05・関連APIへのアクセス可否は本節の行レベル判定のみで決まる（サイドバーの「教材編集」メニュー表示・非表示は、ログインユーザーがオーナー・共同編集者である教材が1件以上存在するかどうかで判定する利便性のための補助表示であり、認可そのものはAPI側の行レベル判定で担保する）。
なぜロールと独立させたか: 要求定義書7章は「教材作成者（author）ロールは、自身が作成した教材のオーナーとしての操作範囲を明確にするためのロールであり、教材の作成・共有自体は全ロール共通の操作」と明記している。したがって教材編集の可否をロールに紐付けると、learner が自作教材を編集できなくなり要求と矛盾する。オーナー・共同編集者という教材単位の行レベル認可をRBACとは別レイヤーとして持つことで、「誰でも教材を作れる」という要求と「教材ごとに編集者を絞る」という要求を両立させている。

5.24 対象外機能

要求事項からは直接求められておらず、本システムでは対象外とする範囲を以下に示す（要求定義書3.2節に対応）。

機能対象外とする理由
学習記録の人事評価・目標管理での利用学習記録は成長支援のための情報とし、人事評価の材料としないことが要求されているため（REQ-N-03）
勤怠管理・給与管理との連携本システムは学習管理を対象とし、人事基幹機能とは連携しない
動画・スライドの編集・加工機能教材ファイルはアップロード・視聴を対象とし、編集・加工は要求されていない（REQ-F-03）
メールによる通知利用者への通知手段はSlackに限定される（制約条件）
プロジェクト所属情報の他システムとの自動連携参照可能な外部システムが現時点で存在しないため初期実装の対象外（9.2節）。プロジェクト所属は自己申告制とする

6.3 共通設計方針

  • 主キー: id は BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY で統一する（T-21のみ key TEXT を主キーとする、Keirekiと同方針）。
  • タイムスタンプ: created_at / updated_at は TIMESTAMPTZ NOT NULL DEFAULT now() で全テーブルに付与する。
  • コード値（role, format, status, mode, type, kind, scope_type）はCHECK制約で許容値を担保する。
  • JSONB項目（options, correct_answer, response, question_order, findings, weak_questions等）は、詳細設計書でスキーマ（フィールド定義）を定める。
  • スキーマ定義は backend/database.py（SCHEMA定義）に集約し、テーブル定義書を docs/ で管理する。

各テーブルのカラム詳細（型・NULL可否・制約・既定値の全定義）は詳細設計書に委ねる。

RLS方針: 全テーブルでRow Level Security（RLS）を有効にする（ALTER TABLE ... ENABLE ROW LEVEL SECURITY;）。アプリケーションは asyncpg で直接接続するため通常アクセスの権限判定（3章のRBAC・オーナー/共同編集者判定）はAPI層で行うが、Supabaseの他経路（PostgREST等）からの意図しない参照を遮断する多層防御として全テーブルRLSを必須とする（Keirekiと同方針）。
