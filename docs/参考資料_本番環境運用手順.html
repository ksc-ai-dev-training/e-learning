3. デプロイ手順（手動）

GitHub Actions（.github/workflows/fly-deploy.yml）によるpush時の自動デプロイは、 現時点では稼働していない（→6章）。そのため、コードの変更を本番に反映するには、 コミット・push とは別に、以下の手動デプロイコマンドを毎回実行する必要がある。

push しただけでは本番に反映されない。 git pushは記録（GitHub上の履歴・共有）のためであり、実際にFly.ioへ反映するには 下記コマンドを別途実行すること。 
cd c:\Users\pc-000683\ai-dev-training\e-learning\e-learning
docker run --rm -it -e FLY_API_TOKEN="（実際のデプロイ用トークン）" -v "${PWD}:/app" fly-cli deploy
  • 実行にはDocker Desktopが起動している必要がある（docker psがエラーになる場合は先にDocker Desktopを起動する）。
  • FLY_API_TOKENには、Fly.io側で発行済みの有効なデプロイ用トークンを渡す。トークンが無効・失効している場合はError: unauthorizedになる（→6章）。
  • 現在の作業ブランチ（basic-design）のワーキングツリーの内容がそのままビルド・デプロイされる。gitのコミット状態に関係なく、コマンド実行時点でローカルにあるファイルがそのまま本番に反映されるため、意図しない未コミットの変更が混ざっていないか、実行前にgit statusで確認すること。

4. DBスキーマ変更の反映

本番（APP_ENV=production）では、起動のたびにCREATE TABLE等を自動実行する 仕組み（AUTO_MIGRATE、backend/database.py）を意図的に無効化している。 そのため、backend/database.pyのSCHEMAにテーブル・カラムの追加/削除を 行った回は、アプリのデプロイ（3章）とは別に、DBスキーマの変更を手動で本番へ反映する必要がある。

反映の順序に注意。 新しいカラムを参照するコードを先にデプロイしてしまうと、そのカラムがまだ無い本番DBに対して エラーになる。先にDBスキーマを反映し、その後でアプリをデプロイすること。

4.1 反映手順

  1. Supabaseの管理画面（https://supabase.com/dashboard）を開き、本番プロジェクトを選択する。
  2. 左メニューの「SQL Editor」を開く。
  3. backend/database.pyのSCHEMA変数のうち、その回で追加・変更したCREATE TABLE IF NOT EXISTS / ALTER TABLE ... ADD COLUMN IF NOT EXISTS / ALTER TABLE ... DROP COLUMN IF EXISTSの該当部分をコピーし、SQL Editorに貼り付けて実行（Run）する。
  4. いずれもIF NOT EXISTS / IF EXISTS付きのため冪等であり、既に反映済みの内容を誤ってもう一度流しても害はない（迷ったらSCHEMA全体を流してよい）。
ローカル開発環境から本番DBへ誤って接続しないこと。 ローカルの.envに本番用のDATABASE_URLを設定したままpython main.pyを 起動すると、DB_MODEの設定に関わらずそちらへ最優先で接続し（backend/database.py）、 かつローカル（APP_ENV≠production）ではAUTO_MIGRATEが既定で有効なため、 schema変更が本番へ意図せず自動適用されてしまう。ローカルの.envのDATABASE_URLは 通常コメントアウトしたままにし（DB_MODE=auto本来のローカルDocker DBに接続させる）、 本番DBへ意図的に接続する必要があるとき（本手順など）だけ、Supabaseの管理画面から直接操作すること。

5. Slack連携（F-12）の設定手順

プロジェクトごとに、必修教材の未受講リマインドを送るSlackチャンネルを1つ設定できる （Incoming Webhook方式。個人ごとのOAuth連携は、社内Slackワークスペースのカスタムアプリ数 上限により利用できなかったため採用していない。検討資料/20260903_Slack連携方式比較.html参照）。

5.1 Webhook URLの発行（Slack側）

  1. https://api.slack.com/appsを開き、対象ワークスペースにログインした状態で、Incoming Webhookが有効になっている既存のアプリを選択する。
  2. 左メニューの「Incoming Webhooks」を開く。
  3. 「Activate Incoming Webhooks」がオフになっていればオンにする。
  4. 下にスクロールし「Add New Webhook to Workspace」をクリックする。
  5. 投稿先チャンネルを選ぶ画面が出るので、リマインドを送りたいチャンネル（プロジェクトごとの専用チャンネル等）を選択し、「許可する」をクリックする。
  6. https://hooks.slack.com/services/xxxx/xxxx/xxxxxxxxxxxxの形式のURLが発行されるので、コピーする。
1つのWebhook URLは、発行時に選んだチャンネル専用に固定される。別のプロジェクト・別のチャンネルに 送りたい場合は、同じアプリから手順1〜6を繰り返し、チャンネルごとに別のURLを発行する。

5.2 ManabiへのURL登録（Manabi側）

  1. Manabiにログインし、対象プロジェクトの「プロジェクト管理」画面を開く。
  2. 「プロジェクト情報」タブの「Slack Webhook URL」欄に、5.1で発行したURLを貼り付ける。
  3. 「保存する」をクリックする。

5.3 リマインドの送信

同じ「プロジェクト情報」タブの「必修教材のリマインドをSlackに送信」ボタンを押すと、 そのプロジェクトの必修教材のうち期限が近い（7日以内）・過ぎていて未完了のものを教材単位で 集計し、5.2で登録したチャンネルへ1メッセージで送信する（個人名は含めない。個人ごとの催促は 「メンバー管理」タブの「未受講の必修教材」一覧を見た管理者が運用で直接連絡する）。 自動送信の仕組みは無く、都度このボタンを押して送信する。

6. 既知の課題

課題内容
GitHub Actions自動デプロイが未稼働 .github/workflows/fly-deploy.ymlはmain/masterブランチへの pushでのみ発火するが、実際の作業ブランチはbasic-designのため、そもそも発火しない。 加えて、GitHub SecretsのFLY_API_TOKENがunauthorizedになる事象も確認されており （手動デプロイで同じ値を使っても再現）、トークン自体の見直しも必要。解消するまでは3章の手動デプロイを継続する。
