7. API設計

7.1 API設計方針

ベースパスは /api とする。認証はセッションJWTとし、ブラウザからのリクエストはHttpOnly Cookie（3.2節）、Claude Code等のCLIクライアントからのリクエストは Authorization: Bearer <token> ヘッダーで送信する（トークンの発行方式は8.2節）。A-01・A-02・A-62（いずれもログイン開始系のエンドポイント）を除く全APIで認証を必須とする。レスポンス形式はJSONを基本とし、教材テキストの往復系API（A-19〜A-21）のみ text/plain; charset=utf-8 を用いる（8.4節）。エラー形式はlcc_crm・Keirekiを踏襲し {"detail": "メッセージ"} とする。権限不足は403、対象なしは404、業務ルール違反（唯一の管理者の削除・降格等）は400、入力形式不正はFastAPI既定の422を返す。権限判定は全てサーバー側（auth_helpers.py の権限デコレーター・依存関数）で行い、下表の「権限」列は3.3節（システム全体ロール）・3.5節（プロジェクトのローカルロール）の判定ロジックに沿って表記する（凡例は7.3節）。

7.2 API一覧（ルーター構成別）

routers/ 配下のファイル単位に、1〜6章で既出のAPI（A-01〜A-61）および本章・8章で新設するAPI（A-62〜A-64）、共有承認フロー（F-26）で新設するAPI（A-65〜A-66）、採点保存API（A-74。v1.26でS-19からS-20へ呼び出し元を変更）・プロフィール自己編集API（A-75〜A-77、v1.22新設）、採点キュー取得API（A-83、S-20用。v1.26新設）、プロジェクト一覧取得API（A-81、S-13教材編集：プロジェクト選択で新設）、S-11・S-12（プロジェクト作成・管理）実装にあたり新設したAPI（A-90〜A-93、v1.39〜v1.42）をまとめて示す（2.4節のファイル構成に対応）。A-05〜A-08・A-23〜A-26は要件定義書v1.5対応（3.4節・5.3節・5.7節）で廃止した機能に対応するAPIであり、欠番として扱う。

7.3 権限列の表記凡例

7.2節の表における「権限」列の表記は、3.3節（システム全体ロール）・3.5節（プロジェクトのローカルロール）の判定ロジックに1対1で対応させている。

表記判定ロジック
不要認証不要（未ログインでも呼び出し可）
認証済（全員）有効なセッションJWT/CLIトークンを持っていればよい（member／admin いずれも可）
adminuser.role == 'admin'（3.3節）
対象プロジェクトの管理者require_project_role(project_id, user, min_role='admin')（3.5節）。システム全体の admin は当該プロジェクトのローカルロールを持たなくても常に満たす
対象プロジェクトの管理者・編集者require_project_role(project_id, user, min_role='editor')
対象教材の受講対象者require_project_role(materials.project_id, user, min_role='learner') を満たすプロジェクトメンバー、または 配信設定（T-11 assignments、F-09）でその教材の対象者として個別に指定されている者、または T-22 material_project_shares で status='accepted' として共有された先のプロジェクトについて require_project_role(shared_to_project_id, user, min_role='learner') を満たす者（F-26、5.27節）、のいずれかを満たすrequire_project_role(materials.project_id, user, min_role='learner') を満たすプロジェクトメンバー、または 配信設定（T-11 assignments、F-09）でその教材の対象者として個別に指定されている者、のいずれかを満たす（2条件。F-26〔教材共有〕は承認時に共有先プロジェクトへ教材の複製を新規作成する方式〔5.27節〕のため、複製後の教材は共有先プロジェクト自身のproject_idを持つ独立レコードとなり、共有専用の第3条件は不要）
本人パス上の user_id／対象 attempt_id の所有者がログインユーザー自身と一致する。A-04・A-75〜A-77のようにパスにIDを取らずJWTのユーザーIDのみを対象とするAPIも同様に「本人」と表記する
対象者が所属するプロジェクトの管理者対象ユーザー（user_id）が現役メンバーであるいずれかのプロジェクトについて require_project_role(project_id, user=リクエスト者, min_role='admin') を満たす（5.19節と同じ判定）
なぜ「対象教材の受講対象者」を独立の判定として設けたか: 3.5節のプロジェクトのローカルロールは、教材が紐づくプロジェクトの現役メンバーであるかどうかのみを見る。しかしF-09（配信対象設定）は、プロジェクトのメンバーでなくても個人単位で受講対象に指定できる（5.9節）。したがって受講系API（A-15, A-28, A-30, A-40〜A-44）の権限判定は require_project_role 単体では閉じず、必ずT-11 assignments の対象者判定とのOR条件になる。この2つの判定はいずれも auth_helpers.py の require_material_access(material_id, user) 依存関数に集約し、個々のルーターが判定ロジックを重複実装しないようにする。
