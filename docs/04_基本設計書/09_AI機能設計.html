9.2 非同期ジョブの実現方式

2章のシステム構成図が示すとおり、本システムはKoyeb上でUvicorn 1プロセスとして稼働し、AIジョブも同一プロセス内で実行する。この制約と、想定規模（社員200名程度）を踏まえ、Redis・Celery等の別プロセスのジョブキュー基盤は導入せず、FastAPIの非同期処理機構のみで非同期ジョブを実現する。

  • 起動: A-42（提出）・A-34（つまずき分析）・A-48（組織レポート）・A-51（個人フィードバック）は、リクエストを受けたらまず結果テーブル（T-16〜T-18）にrequested_at=now()のプレースホルダ行を同期的に作成し（内容カラムはNULLのまま）、その後でAI呼び出しを asyncio.create_task（FastAPIのBackgroundTasks相当）でスケジュールし、即座に202相当のレスポンス（受付済みを示すJSON）を返す。Uvicornのイベントループ上でAI呼び出し（ネットワークI/O待ち）が進む間も、他のリクエスト処理はブロックされない。
  • ジョブ状態の表現（専用のジョブテーブルを持たない）: ジョブの進行状況は、対応する結果テーブル（T-14のai_score_pct／T-16 ai_material_insights／T-17 ai_personal_feedback／T-18 ai_org_reports）自体の状態で表現する。T-16〜T-18は該当機能の実行ごとに行が作成される設計のため、「対象の行が存在しない」＝処理中、「行が存在する」＝完了として扱う。T-16〜T-18は上記のとおりリクエスト受付時に行を作成するため、「内容カラムがNULL」＝処理中、「内容カラムが設定済み」＝完了として扱う。T-14（記述式採点）は既存行のai_score_pctがNULLのままであれば「採点中」である（5.14節ですでに定義済み）。
  • 取得（ポーリング）: フロントエンドはA-35/A-43/A-49/A-52をSWRの再検証間隔付きで呼び出し、結果が存在するまで数秒間隔でポーリングする。WebSocket等のプッシュ通知は本フェーズでは導入しない（想定規模・実装コストに見合わないため）。
  • 失敗時のリトライ: Claude API呼び出しが失敗した場合、ジョブ内で指数バックオフにより最大3回リトライする（要件定義書6.2節）。全て失敗した場合も当該行は削除せず内容カラムをNULLのまま残し（学習記録自体は失われない、REQ-N-05）、構造化ログ（10.4節）にエラーを記録する。フロントエンドは一定時間（目安3分）応答がない場合に「時間がかかっています」の案内を表示し、再試行操作（同一APIの再呼び出し）を可能にする。
  • プロセス再起動・デプロイによるジョブ消失への対策: asyncio.create_taskでスケジュールしたタスクはプロセスのメモリ上にのみ存在するため、Koyebのデプロイ（10.5節、mainマージ即時反映）やクラッシュでプロセスが再起動すると、実行中のタスクはリトライも記録も残らず消える。この場合でも上記のプレースホルダ行（requested_atあり・内容カラムNULL）は残るため、これを起点に検出・復旧する。具体的には、アプリ起動時（lifespanイベント）およびその後5分ごとに、requested_atが10分以上前かつ内容カラムがNULLの行（T-16〜T-18）と、submitted_atが10分以上前かつai_score_pctがNULLの回答（T-14）を検出し、AI呼び出しを再スケジュールする「スタックジョブ・スイープ」を実行する。これにより、途中で失われたジョブも次回のスイープで自動的に再試行され、受講者・教材編集者が結果を永久に待ち続ける状態を防ぐ。専用のジョブキュー基盤（Redis・Celery等）を導入しない9.2節の方針を維持したまま、想定規模（社員200名程度、デプロイ頻度は開発時のみ高い）に見合う最小限の復旧策とする。

9.3 AI利用ログ（T-19 ai_usage_logs）の記録方式

Claude APIの呼び出しは、必ず共通クライアント（ai_client.py）を経由させる。ai_client.pyは呼び出しの成否によらず、呼び出し完了時にT-19へ1行記録する。

  • feature: 呼び出し元機能を識別する固定値（material_review / grading / insight_analysis / personal_feedback / org_report / draft_assist（F-27、A-69。F-27はv1.20で廃止したため今後この値が記録されることはない））。
  • model: 実際に呼び出されたモデルID（9.4節の優先順位で解決された値）。
  • input_tokens・output_tokens: Messages APIのレスポンスに含まれるトークン数をそのまま記録する。
  • cost_estimate: input_tokens × 単価_in + output_tokens × 単価_outで概算する。モデルごとの単価はai_client.py内の定数テーブルとして保持し、Anthropicの価格改定時にはこの定数を更新する（本書では具体的な単価は定めない）。通貨は画面モックアップ（S-10）に合わせ円（JPY）で表示する。
  • 内容そのものは記録しない: 要件定義書6.2節・Keirekiのai_usage_logsと同方針で、プロンプト・レスポンスの本文は保存しない。
AI利用費用の管理方法（要件定義書9.2節「別途整理する」の対応）: S-10のシステム設定タブは、当月のトークン数・概算コストの表示（既に画面モックアップで確定済み）のみを持つ。本設計ではこれに加え、環境変数AI_MONTHLY_BUDGET_ALERT_JPY（任意設定、既定は未設定＝アラートなし）を導入する。ai_client.pyはAPI呼び出し完了時に当月のcost_estimate合計を集計し、閾値を超えた場合は10.4節の構造化ログに警告レベルで記録する。画面上の新たな設定項目を追加すると4章（画面設計）の確定済み内容に踏み込むため、本フェーズでは環境変数による運用者向けの目安機能に留め、S-10でのUI化（閾値入力欄・Slackアラート連携等）は将来の拡張として詳細設計以降で検討する。

9.4 モデル選択の実現方式

利用するモデルは、要件定義書6.2節・2.2節の方針どおり「画面設定 > 環境変数 > 既定値」の優先順位で解決する。

  1. 画面設定: T-21 app_settings（key='ai_model'）に値があればそれを使う（S-10「利用するAIモデル」プルダウン、A-56で更新）。
  2. 環境変数: 画面設定が未設定の場合、環境変数ANTHROPIC_MODELを使う（2.3節）。
  3. 既定値: いずれも未設定の場合、claude-sonnet-5を使う（2.2節）。

選択可能な値はclaude-sonnet-5 / claude-opus-5 / claude-haiku-4-5の3種に限定し（S-10プルダウンの選択肢、2.2節）、ai_client.pyはこれ以外の値が設定されていた場合は既定値にフォールバックしたうえで警告ログを出す。全AI機能（F-08, F-20〜F-23）で同一のモデル設定を共有し、機能ごとの個別設定は持たない（S-10の画面が単一のプルダウンであるため、5機能を横断する単一の設定として扱う）。

9.6 Claude API共通呼び出し設計（ai_client.py）

  • 構造化出力: 教材レビュー（F-08）・つまずき分析（F-21）のように「指摘事項のリスト」「分析結果＋提案」を返す機能は、Claude APIのツール呼び出し（tool use）を用いて構造化されたJSONで応答を受け取り、パース失敗時のフォールバック処理を挟まない設計とする。
  • タイムアウト・リトライ: 1回の呼び出しにつきタイムアウトを設定し（詳細設計で定める）、9.2節のリトライ方針（指数バックオフ最大3回）を共通実装する。
  • モデル解決・ログ記録: 9.4節のモデル解決、9.3節のT-19記録はai_client.py内で一元的に行い、各機能の呼び出し元（materials.py, learning.py, dashboard.py, reports.py）はモデル名やログ記録を意識しない。
