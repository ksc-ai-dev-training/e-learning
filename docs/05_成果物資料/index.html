1. はじめに

1.1 本書の位置づけ

本書は、社内学習管理システム（コードネーム: Manabi）の要求仕様書（v1.0）・要件定義書（v1.20）・基本設計書（v1.26）で定めた機能（F-01〜F-29）・画面（S-01〜S-19）・API（A-01〜A-80）・テーブル（T-01〜T-29）を、実装可能なレベルまで網羅的に詳細化するものである。対象読者は本システムの実装担当者とする。

  • ID体系（REQ-xx=要求 / F-xx=機能 / S-xx=画面 / T-xx=テーブル / A-xx=API）は要求仕様書・要件定義書・基本設計書と共通であり、本書ではIDを用いて相互参照する。廃止・欠番のIDは基本設計書の扱いをそのまま引き継ぐ（F-03, F-07, F-27／S-07, S-18／T-02, T-05, T-07, T-24, T-25／A-05〜A-08, A-23〜A-26, A-68〜A-70）。
  • 上流文書は要求仕様書（docs/01_要求仕様書.html）・要件定義書（docs/02_要件定義書.html）・基本設計書（docs/04_基本設計書/）の3文書とする。
  • 技術スタックは既存システム LCC CRM・Keireki を踏襲する（REQ-N-06）。Frontend: React 19 + TypeScript + Vite 6 + Tailwind CSS 4 + react-router 7 + SWR + Lucide React、Backend: FastAPI (Python 3.10+) + Uvicorn + asyncpg、Database: PostgreSQL (Supabase)、ファイルストレージ: Supabase Storage、AI連携: Anthropic Claude API（Messages API）、通知: Slack Incoming Webhook、ホスティング: Koyeb。
  • 本書は実装担当者がそのまま実装に移せることを目的とし、機能・画面・API・テーブルを網羅する。CRUD系のように処理が定型的なものは記載を簡潔にするが、対象から省略することはしない。
  • 各テーブルのカラム詳細（型・NULL可否・制約・既定値の全定義）、API詳細、画面項目定義、教材連携・AI機能の実装レベルの仕様は本書で定める。画面レイアウトそのものは画面モックアップ「03_画面モックアップ/」を正とし、本書では重複して図示しない。

2. 実装構成

ディレクトリ構成はLCC CRM・Keirekiのコード規約に準拠する。バックエンドはルーター分割方式、フロントエンドは pages / components / hooks 分割方式とする（基本設計書2.4節を詳細化）。

Manabi/
├── backend/
│   ├── main.py               # FastAPIアプリ生成、ルーター登録、静的配信（本番SPA）、CORS/起動設定、lifespanでスタックジョブ・スイープを起動（8.2節）
│   ├── database.py           # asyncpg接続プール管理、SCHEMA定義（CREATE TABLE文・RLS有効化文、3章）、初期データ投入（「全社公開」プロジェクト）

2.2 設計方針

keireki詳細設計書分冊3（12.1節）と同方針。実装が進むほど効いてくる決めごとなので、実装より先に本節で固定する。

方針内容
レイヤー分割pages/（画面＝ルート単位）→ components/（画面横断の部品）→ components/ui/（フォーム部品）の3階層。hooks/（データ取得）・lib/（APIクライアント）・types/（API型）はUIを持たない
サーバー状態SWRで取得・キャッシュする（2.5節）。取得ロジックはhooks/のカスタムフックに包み、ページからuseSWRを直接呼ぶのは画面固有で再利用しない取得（S-01の開発用ユーザー一覧等）に限る
UI状態タブ選択・フォーム入力値・モーダル開閉などはコンポーネントローカルのuseStateに置く。Redux / Zustand等のグローバルストアは導入しない
横断的な関心React Contextはトースト通知（ToastProvider）と確認ダイアログ（ConfirmProvider）の2つだけとし、main.tsxでアプリ全体を包む（2.1.4節）。現状S-01のみでどちらも未使用のため未導入。S-02以降でどちらかが最初に必要になった画面で導入する
更新の反映保存系API（PUT/POST/DELETE）の後は、該当フックのmutate()で再取得する（楽観的更新はしない）
Propsの向きデータは親→子へPropsで渡し、子→親はコールバック（onSaved / onClose / onChange）で通知する
権限による出し分けuseMe()のrole（'member'/'admin'、T-01）で判定する。Manabiはこれに加えプロジェクト単位のローカルロール（T-04 project_memberships.role: 'admin'/'editor'/'learner'）を持つため、プロジェクト配下の画面（S-05教材編集等）はグローバルロールとローカルロールの2段階で判定する（基本設計書3.5節）。判定箇所はルート（App.tsx）・メニュー・ボタンの3箇所に限り、権限の正はサーバー側にある
スタイルTailwind CSSのユーティリティをJSXに直接書く。共通の見た目が複数箇所で必要になったら、keirekiのcomponents/ui/shared.tsxに倣ったクラス生成関数を追加する（現状S-01は単純なため未導入）
検索条件の状態管理複数項目の絞り込み（S-14等）は、入力中の値（form）と一覧に適用済みの値（filter）を分け、「絞り込む」ボタン押下でfilterに反映する（keirekiのCareerList・12.3節と同方針）。入力のたびに即時反映する単一項目の検索（S-13のプロジェクト名検索）はこの限りでない

2.8 APIクライアントとエラー処理（frontend/src/lib/api.ts）

  • apiFetch<T>(path, init?): credentials: 'same-origin'・Content-Type: application/jsonを既定にしたfetchラッパー。2xxならJSONをTとして返し（204はundefined）、それ以外はApiError(status, detail)をthrowする。detailはAPIのエラーレスポンス形式（9章）から取り、JSONでなければ「エラーが発生しました」
  • apiFetchText(path, body): A-20（PUT /source）専用。リクエスト・レスポンスともtext/plainのためapiFetchとは別関数にし、401処理・ApiErrorthrowのみ共通化した。S-05の目次構造編集（lib/materialSource.ts）から使う
  • 401の共通処理: /api/auth/以外のパスで401を受けたらwindow.location.href = '/login'でログイン画面に飛ばす（セッション切れ対策）。useMeが使う/api/auth/meは除外し、401を「未ログイン」として扱う
  • 表示の使い分け: 取得失敗（SWRのerror）は画面内に赤文字で表示、保存・削除の結果は将来useToast()導入後にそちらへ移す（現状Loginはログイン失敗をローカルstateで直接表示）。alert / window.confirmは使わない。削除確認は本来ConfirmProvider（2.2節）で統一するが未導入のため、S-05の章・小見出し削除は暫定的に行内で「本当に削除？」表示に切り替える簡易確認とした。ConfirmProvider導入時に置き換える

2.9 コンポーネント追加・変更時の規約

  1. 新しい画面（S-xx）はpages/に1ファイルで作り、App.tsxのRoutesに追加する。ロールで制限する場合はApp.tsxでリダイレクトし、同時にサーバー側のガード（5章）があることを確認する
  2. タブが3つ以上ある画面はpages/<画面>/にタブごとのファイルを分け、親は切替とonSavedの配布だけを行う（keirekiのS-04/S-05と同じ構造）
  3. 2画面以上で使う部品はcomponents/に、1画面内でしか使わない部品は同じファイル内の非公開関数コンポーネントにする（export しない）
  4. フォーム部品は必ずcomponents/ui/の部品を使う（2.1.5節の実装規約）。新しい入力形式が必要になったらui/に追加し、2.1節の表と2.7節にPropsを追記する
  5. APIを追加したらtypes/index.tsにレスポンス型を追加し、参照が複数箇所ならhooks/にフックを作る（2.5節の基準）
  6. localStorageにキーを追加するときはmanabi-プレフィックスを付け、2.6節の表に登録する
  7. コンポーネントの冒頭コメントに対応する画面IDと詳細設計書の章番号を書く（例: // S-02 マイ学習（詳細設計書 10.2））
