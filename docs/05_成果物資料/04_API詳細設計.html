4. API詳細設計

ベースパスは/api。認証はセッションJWT（HttpOnly Cookie）またはCLIトークン（Authorization: Bearer、7.4節）。エラー形式は{"detail": "メッセージ"}に統一する（9章）。403は権限不足、404は対象なし、400は業務ルール違反、422はPydanticバリデーションエラーを表す。権限列の表記は基本設計書7.3節の凡例（require_project_role等）に対応する。本章は router ファイル単位に基本設計書7.2節の一覧を実装レベルへ詳細化する。処理が単純なCRUD（作成・単純更新・削除・単純一覧）は一覧表の「リクエスト／レスポンス」列で仕様を尽くし、業務ロジックを伴うAPIのみ個別に処理フローを記す（研修サンプルとしての方針、1.1節）。

A-75/A-76 処理フロー（アイコンアップロードの2段階方式）: (1) フロントエンドはファイル選択後、A-76へfilename・mime_type・size_bytesを送信し、Supabase Storageへの署名付きアップロードURLとstorage_key（user-icons/{user_id}/{uuid}.png形式）を受け取る。(2) 受け取ったURLへブラウザから直接ファイルをアップロードする（バックエンドを経由しない、A-27と同じ方式）。(3) アップロード完了後、A-75へicon_storage_keyを送信してusers.custom_picture_keyを確定する。(2)が失敗した場合、(3)を呼ばなければcustom_picture_keyは更新されず、Storage上には孤立したオブジェクトが残る（教材添付ファイルと同様、当面は許容し、必要になった時点で未参照オブジェクトの定期削除バッチを検討する）。

A-02 処理フロー（基本設計書3.1節・8.2節を実装レベルへ）:

  1. state をCookie保存値と定数時間比較で照合。不一致・欠落はerror=invalid_requestでリダイレクト（Googleと通信しない）
  2. code をGoogleトークンエンドポイントでIDトークンに交換し、署名（JWKS・RS256）・発行者・audienceを検証
  3. email_verifiedがtrueであることを検証（falseはerror=forbidden）
  4. emailのドメインをALLOWED_DOMAINS（既定 kogasoftware.com）と照合（不一致はerror=domain）
  5. T-01 usersをemailで検索（大文字小文字を区別しない）。存在しなければrole='member', is_active=trueで新規登録し、この初回登録時のみGoogleプロフィールの氏名をnameの初期値として設定する（初回ログイン）。既存ユーザーの場合はnameを更新しない（本人がS-15で変更した表示名をGoogle側の氏名変更で上書きしないため。F-29、基本設計書v1.22）。picture_url相当のGoogleプロフィール画像はDBに保存せず、A-04・A-75で参照する都度Googleから取得する
  6. 初回登録の場合のみ: トランザクション内でT-04 project_membershipsに、is_company_wide=trueのプロジェクトIDに対するrole='editor', status='active', joined_at=now(), assigned_by=NULLの行を追加する（基本設計書5.25節）
  7. is_active=falseのユーザーはログイン拒否（error=inactive）
  8. JWT（sub=users.id, role, token_type='session', 有効期限）をJWT_SECRETで署名し、HttpOnly / Secure（本番） / SameSite=Lax のCookieに設定
  9. 構造化ログ event=login（成功）またはevent=login_denied（拒否理由つき、9.3節）を記録し、302で/（成功）または/login?error=<種別>（拒否）へ
error種別条件S-01の表示

A-74（新設）の位置づけ: 基本設計書はS-19（設問別の回答・結果一覧）の「採点する」「採点を修正」ボタンが呼ぶAPIを明示的に「詳細設計で定義する」としていた（4.7c節）。本書でA-73（GET、一覧取得）と対になる更新APIとしてA-74を新設する。grading_mode='ai'の設問（AI採点結果の訂正）・grading_mode='manual'の設問（担当者による新規採点）のいずれも同一APIで扱う: リクエストのis_correct・ai_feedbackで対象answers行を更新し、reviewed_by=リクエストユーザー, reviewed_at=now()を設定する。ai_score_pctは変更しない（AIが算出した参考値として保持し、人手の判断はis_correctのみで表現する）。更新後は4.5節A-42と同じ正答率再計算・合否判定ロジックを呼び出し、当該attempt_idのquiz_attempts.score_pct・passedを確定させる（採点確定によって「採点中」状態から合否が決まるケースを含む）。

A-40 処理フロー:

  1. mode='graded'の場合、SELECT * FROM quiz_attempts WHERE user_id=? AND material_id=? AND mode='graded' AND scope_node_id IS NOT DISTINCT FROM ? AND submitted_at IS NULLで未提出の試行を検索。存在すれば200でその試行の内容（対象ページの本文・設問）を返す（続きから再開）
  2. 未提出の試行が無ければ新規作成。attempt_noは同一(user_id, material_id, scope_node_id, mode='graded')の既存件数+1
  3. materials.attempt_scopeに応じて対象ノード群を決定する（'material'なら全ページ、'chapter'/'section'/'page'ならscope_node_id配下の全ページ）
  4. 対象ページのうちquiz_mode='pool'のページは、pool_group_idごとにグルーピングした設問からランダムにpool_draw_count件を抽出し、抽出結果のquestion_id配列をquestion_orderに記録する（quiz_mode='all'のページは全問をそのままquestion_orderに記録）
  5. 201で試行ID・対象ページの本文（サニタイズ済み）・設問（correct_answer・scoring_criteriaを含まない受講者向け形式）を返す

A-42 処理フロー（採点・合否判定）:

  1. 当該試行に紐づく全answersを取得し、対象設問（question_orderに含まれるもの。carried_over_question_idsを含む再受験の場合はそれも合算）と突き合わせる
  2. type IN ('single','multi','reorder')はresponseとcorrect_answerを比較して即時is_correctを確定
  3. type IN ('free_text','code')は、当該設問のgrading_mode（未設定なら教材既定）が'ai'ならAI採点ジョブを非同期起動（8.2節）、'manual'ならis_correct・ai_score_pctをNULLのまま据え置く（後日S-19で担当者が採点）
  4. type='score_log'は正誤判定を行わず、正答率算出の分母（対象設問数）からも除外する
  5. 正答率: score_pct = 正解数 ÷ (対象設問数 − score_log設問数 − 未採点のfree_text/code設問数)。free_text/code設問がAI採点待ち・手動採点待ちで1件でも残る間はscore_pct・passedともNULLのまま「採点中」とし、最後の1件が確定した時点で本APIと同じ集計ロジックを再実行して確定させる（8.2節「非同期ジョブの実現方式」の一部としてAI採点ジョブの完了処理内に同居させる）
  6. ドボン問題判定: 対象設問のうちis_critical=trueの設問に1つでも不正解があれば、他の正答率によらずpassed=falseとし、fail_reasonに該当設問のpromptを記録する
  7. 上記のいずれにも該当しなければ、materials.assignments（当該試行のscope_typeに対応するもの。無ければ教材既定は存在しないため配信設定側のpass_score_pctを必ず参照）のpass_score_pctとscore_pctを比較してpassedを確定する
  8. submitted_at=now()を設定し、mode='graded'なら6.6節の進捗更新（T-12）も行う
