5.1 auth_helpers.py の依存関数一覧

5.2 require_project_role の実装

ROLE_RANK = {"learner": 1, "editor": 2, "admin": 3}

async def require_project_role(project_id: int, min_role: str):
    async def checker(request: Request) -> User:
        user = await require_auth(request)
        if user.role == "admin":
            return user   # システム全体のadminは常に許可（保守目的）
        row = await conn.fetchrow(
            """SELECT role FROM project_memberships
                WHERE project_id = $1 AND user_id = $2
                  AND status = 'active'""",
            project_id, user.id)
        if row is None or ROLE_RANK[row["role"]] < ROLE_RANK[min_role]:
            raise HTTPException(403, detail="この操作を行う権限がありません")
        return user
    return checker

status != 'active'（招待中invited・辞退declined）のメンバーはロールを問わず不許可となる。left_at IS NOT NULL（削除済み）の行はそもそもstatusを条件に含めても除外されない可能性があるため、実装上はWHERE ... AND status = 'active' AND left_at IS NULLとする（削除時にstatusは変更しないため。4.2節A-13参照）。

実装との対応（S-05着手分）: 本節のrequire_project_role・5.1節のrequire_material_editorは、実装ではbackend/auth_helpers.pyのcheck_project_role(user, project_id, min_role)（本文だけの判定関数）と、それを使うrequire_project_role(min_role)／require_material_role(min_role)という2つのFastAPI依存性ファクトリに分かれている。require_material_roleは教材IDパスパラメータからproject_idを引いてcheck_project_roleに委譲する点は本節の設計通りだが、加えて全社Wikiプロジェクトの下書き制限（is_company_wide_draft_restricted）も行う：教材がstatus='draft'かつ所属プロジェクトがis_company_wide=trueの場合、作成者本人・そのプロジェクトの管理者・システムadmin以外は403にする。全社Wikiは全社員が自動でeditorになる特殊プロジェクトのため、下書きが他メンバーに意図せず見られてしまう問題があり追加した（教材保存時のフィードバックを受けて2026-08-27追加）。A-21（教材一覧）も同じ条件で一覧から除外する。全社Wiki以外の（招待制の）プロジェクトはメンバーが元々限定されているため、この追加制限は適用しない。

5.3 require_material_access の実装（受講対象者判定）

基本設計書7.3節が定める「対象教材の受講対象者」のOR条件を1つの依存関数に集約する。個々のルーターが判定ロジックを重複実装しないようにするための共通化である。2条件（当初3条件から簡素化。2026-08-28）: F-26（教材共有、基本設計書5.27節）を「共有先には権限だけを付与する参照共有モデル」から「承認時に共有先プロジェクトへ教材の複製を新規作成する複製モデル」に変更したことに伴い、複製後の教材は共有先プロジェクト自身のproject_idを持つ独立レコードになるため、共有先メンバーは条件1（プロジェクトの現役メンバー）だけで自然にアクセスでき、専用の「条件3: 共有先メンバーシップ」は不要になった。

async def require_material_access(material_id: int):
    async def checker(request: Request) -> User:
        user = await require_auth(request)
        if user.role == "admin":
            return user
        material = await fetch_material_scope_row(material_id)  # project_id, status
        # 条件1: 教材が紐づくプロジェクトの現役メンバー（受講者以上）
        is_project_member = await has_active_project_role(
            material["project_id"], user.id, min_role="learner")
        if is_project_member:
            return user
        # 条件2: 配信設定（T-11 assignments）で個人指定されている
        is_individual_target = await conn.fetchval(
            """SELECT EXISTS(
                 SELECT 1 FROM assignments
                  WHERE material_id = $1 AND scope_type = 'individual'
                    AND scope_id = $2)""",
            material_id, user.id)
        if is_individual_target:
            return user
        raise HTTPException(403, detail="この教材の受講対象ではありません")
    return checker
なぜ2条件のORが必要か: プロジェクトのローカルロール（5.2節）だけでは、プロジェクトのメンバーでない社員を個人指定で受講対象に加える配信設定（F-09）を表現できない。この2条件は「教材が紐づく1つのプロジェクトのメンバーであること」を必須としない設計であり、必ずどちらか1つを満たせばよい。教材のプロジェクト間共有（F-26）は、共有先プロジェクトへ教材そのものの複製を作る方式（複製モデル）のため、この判定関数に共有専用の条件を追加する必要はない（共有先の複製は、その複製自身のproject_idに対する条件1で自然にアクセスできる）。
実装上の注意（F-26着手時）: F-26実装前の設計検討過程では「共有先プロジェクトのメンバーである」という条件3の追加が一時的に構想されていた（`material_project_shares`テーブルを参照する版）。この構想は複製モデルの採用により不要になったため、F-26に着手する際は本節の2条件版を正とし、既存コードのコメント等に「条件3を追加する」という古い記述が残っていても従わないこと（基本設計書5.27節「参照共有モデルから複製モデルへ変更した理由」を参照）。

5.4 「対象者が所属するプロジェクトの管理者」判定

S-09（個人学習レポート）・A-50〜A-52で使用する。対象ユーザー（user_id）が現役メンバーであるいずれかのプロジェクトについて、リクエスト者がrequire_project_role(min_role='admin')を満たすかを判定する（基本設計書7.3節と同じ判定）。

async def is_manager_of_target_user(target_user_id: int, requester: User) -> bool:
    if requester.role == "admin":
        return True
    target_project_ids = await conn.fetch(
        """SELECT project_id FROM project_memberships
            WHERE user_id = $1 AND status = 'active' AND left_at IS NULL""",
        target_user_id)
    for row in target_project_ids:
        if await has_active_project_role(
                row["project_id"], requester.id, min_role="admin"):
            return True
    return False

5.5 プロジェクト離任後の猶予期間判定

基本設計書5.25節の猶予期間ロジックを、5.3節のhas_active_project_roleを拡張する形で実装する。「現役メンバー」または「削除から猶予日数以内」のいずれかを満たせば受講権限を継続する。

async def has_active_project_role(project_id: int, user_id: int, min_role: str) -> bool:
    row = await conn.fetchrow(
        """SELECT role, status, left_at FROM project_memberships
            WHERE project_id = $1 AND user_id = $2""",
        project_id, user_id)
    if row is None:
        return False
    if row["status"] == "active" and row["left_at"] is None:
        return ROLE_RANK[row["role"]] >= ROLE_RANK[min_role]
    if row["left_at"] is not None:
        grace_days = await get_setting_int(
            "project_leave_grace_period_days", default=30)
        if row["left_at"] + timedelta(days=grace_days) >= datetime.now(timezone.utc):
            # 猶予期間中は「受講者」相当のアクセスのみ継続する（編集権限は即時失効）
            return min_role == "learner"
    return False
猶予期間中は受講権限のみ継続する: 基本設計書5.25節の設計判断のとおり、ロール降格そのものは猶予期間の対象外とし、プロジェクトから削除された場合のみ猶予期間が発生する。上記実装ではleft_atが設定された行に対してはmin_role == "learner"のときのみtrueを返すことで、「猶予期間中でも教材の新規編集はできない（即時失効）が、既に配信された教材の閲覧・受講は継続できる」という非対称な扱いを表現している。

5.6 フロントエンド側のガード

frontend/src/App.tsxでA-04（/api/auth/me）の結果とS-11「自分が参加しているプロジェクト」の集計に基づきルート・メニュー表示を制御する。権限の正はサーバー側検証（5.1〜5.5節）であり、以下はUX目的の表示制御に過ぎない。

  • 未認証（A-04が401）→ S-01（/login）へリダイレクト
  • 「教材編集」メニュー: 常時表示（全社員が「全社Wiki」プロジェクトの編集者を自動的に持つため、実質的に誰でもS-13へ進める。基本設計書4.2節）
  • 「プロジェクト管理」メニュー（S-12への導線）: 自分が管理者であるプロジェクトが1件以上ある場合のみ表示
  • 「受講状況ダッシュボード」（S-08）・「配信設定」（S-06）メニュー: adminは常時表示。member はプロジェクト管理者であるプロジェクトが1件以上ある場合のみ表示（自プロジェクト範囲）
  • 「システム管理」メニュー（S-10。表示ラベルのみ「システム管理」、画面自体の名称はS-10「管理」のまま）: adminのみ表示（実装済み、2026-09-02。NAV_ITEMSで初めてadminOnlyによるロール限定表示を導入した）
  • S-19（設問別の回答・結果一覧）へのリンク: S-05・S-17の設問カードで、当該教材のプロジェクトの管理者/編集者、またはadminにのみ表示
重要: フロントエンドのメニュー出し分けはあくまで表示制御（UX目的）であり、権限の正はサーバー側検証（5.1〜5.5節）である。URL直打ちやAPI直接呼び出しが行われても、全APIがauth_helpers.pyの依存関数で検証するため越権操作はできない。

5.7 子リソースの所属検証（2026-09-02、網羅的コードレビューで発見・修正）

処理概要: 5.1〜5.6節の「プロジェクト・教材への権限」に加え、書き込み系APIには「リクエストボディで指定した子リソースID（設問ID・ノードID・アンケート設問IDなど）が、実際に権限確認済みの親リソースに属するか」という別種の検証が必要になる。権限自体は正しく確認していても、この所属検証が漏れていると、権限のある操作（例: 自分が受講中の教材への回答保存）を経由して権限の無いリソース（例: 非公開の別教材の設問）を不正に参照・汚染できてしまう。網羅的コードレビューで、以下3件がこの所属検証を欠いていたことが判明し修正した。

API欠けていた検証影響
A-41 PUT /api/attempts/{attempt_id}/answersquestion_idが当該attemptのmaterial_idに属するか非公開の別教材の設問IDを指定すると、AIがそのまま採点・講評を返し、正解の内容を実質的に探り当てられた。修正: SELECT ... FROM questions WHERE id = $1 AND material_id = $2（attempt.material_idで絞り込み）
A-29 POST /api/materials/{id}/attachmentsnode_idが対象教材idのノードか別教材のノードIDを指定した添付行が作成され、material_id/node_idの不整合なレコードが残る。修正: 事前にmaterial_nodesへの所属を確認し、一致しなければ422
A-72 POST /api/surveys/{survey_id}/responsessurvey_question_idが対象survey_idの設問か別アンケートの設問IDを指定すると、そのアンケートの集計にデータが混入する。修正: 保存前にsurvey_questionsへの所属を一括確認し、一致しなければ422

類似のAPI（replace_questions・upsert_survey）は元々この種の所属検証を行っており、上記3件だけが漏れていた。今後、子リソースIDを受け取る新規APIを追加する際は、この所属検証を必ずセットで実装すること。

5.8 ローカル開発用ファイル配信の署名付きURL（2026-09-02、網羅的コードレビューで発見・修正）

処理概要: 本番（SUPABASE_URL設定時）はA-27/A-30がSupabase Storageの署名付きURL（対象storage_key限定・600秒で失効）を返すが、ローカル開発専用の代替経路（backend/routers/uploads.py）はrequire_authのみで、storage_keyさえ知っていれば認証済みの任意のユーザーが無期限に閲覧・上書きできてしまっていた。本番と同等の保護をローカルでも持たせるため、storage.pyにmake_local_signed_query/verify_local_signed_query（HMAC-SHA256、JWT_SECRETを鍵としてstorage_key:expiresに署名、600秒で失効）を新設し、A-27（create_upload_target）・A-30（create_download_url）が返すローカルURLに?expires=...&sig=...クエリを付与、uploads.pyのGET/PUTでこれを検証するようにした。署名が無い・期限切れ・別のstorage_key向けの署名を流用した場合はいずれも403で拒否する。本番環境（Supabase Storage使用時）はこの経路自体を通らないため影響しない。
