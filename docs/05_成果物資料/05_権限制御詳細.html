5. 権限制御詳細

5.1 auth_helpers.py の依存関数一覧

依存関数シグネチャ判定内容
require_auth(request) -> User有効なセッションJWT／CLIトークンを持つこと（role不問）。無効・欠落は401
require_roles(*roles)(request) -> Useruser.roleが指定ロールのいずれかであること（例: require_roles("admin")）。不足は403
require_project_role(project_id, min_role)(request) -> User5.2節参照。user.role == 'admin'は常に許可（プロジェクトロール不問）
require_material_access(material_id)(request) -> User5.3節参照（受講対象者判定のOR条件）
require_material_editor(material_id)(request) -> User対象教材のproject_idを取得しrequire_project_role(project_id, min_role='editor')に委譲する薄いラッパー

5.2 require_project_role の実装

ROLE_RANK = {"learner": 1, "editor": 2, "admin": 3}

async def require_project_role(project_id: int, min_role: str):
    async def checker(request: Request) -> User:
        user = await require_auth(request)
        if user.role == "admin":
            return user   # システム全体のadminは常に許可（保守目的）
        row = await conn.fetchrow(
            """SELECT role FROM project_memberships
                WHERE project_id = $1 AND user_id = $2
                  AND status = 'active'""",
            project_id, user.id)
        if row is None or ROLE_RANK[row["role"]] < ROLE_RANK[min_role]:
            raise HTTPException(403, detail="この操作を行う権限がありません")
        return user
    return checker

status != 'active'（招待中invited・辞退declined）のメンバーはロールを問わず不許可となる。left_at IS NOT NULL（削除済み）の行はそもそもstatusを条件に含めても除外されない可能性があるため、実装上はWHERE ... AND status = 'active' AND left_at IS NULLとする（削除時にstatusは変更しないため。4.2節A-13参照）。

5.3 require_material_access の実装（受講対象者判定）

基本設計書7.3節が定める「対象教材の受講対象者」のOR条件を1つの依存関数に集約する。個々のルーターが判定ロジックを重複実装しないようにするための共通化である。

async def require_material_access(material_id: int):
    async def checker(request: Request) -> User:
        user = await require_auth(request)
        if user.role == "admin":
            return user
        material = await fetch_material_scope_row(material_id)  # project_id, status
        # 条件1: 教材が紐づくプロジェクトの現役メンバー（受講者以上）
        is_project_member = await has_active_project_role(
            material["project_id"], user.id, min_role="learner")
        if is_project_member:
            return user
        # 条件2: 配信設定（T-11 assignments）で個人指定されている
        is_individual_target = await conn.fetchval(
            """SELECT EXISTS(
                 SELECT 1 FROM assignments
                  WHERE material_id = $1 AND scope_type = 'individual'
                    AND scope_id = $2)""",
            material_id, user.id)
        if is_individual_target:
            return user
        # 条件3: status='accepted' で共有された先のプロジェクトの現役メンバー
        shared_project_ids = await conn.fetch(
            """SELECT shared_to_project_id FROM material_project_shares
                WHERE material_id = $1 AND status = 'accepted'""",
            material_id)
        for row in shared_project_ids:
            if await has_active_project_role(
                    row["shared_to_project_id"], user.id, min_role="learner"):
                return user
        raise HTTPException(403, detail="この教材の受講対象ではありません")
    return checker
なぜ3条件のORが必要か: プロジェクトのローカルロール（5.2節）だけでは、プロジェクトのメンバーでない社員を個人指定で受講対象に加える配信設定（F-09）を表現できない。また教材のプロジェクト間共有（F-26）も、共有先プロジェクトのメンバーという別経路でのアクセスを許可する必要がある。この3条件は「教材が紐づく1つのプロジェクトのメンバーであること」を必須としない設計であり、必ずどれか1つを満たせばよい。

5.4 「対象者が所属するプロジェクトの管理者」判定

S-09（個人学習レポート）・A-50〜A-52で使用する。対象ユーザー（user_id）が現役メンバーであるいずれかのプロジェクトについて、リクエスト者がrequire_project_role(min_role='admin')を満たすかを判定する（基本設計書7.3節と同じ判定）。

async def is_manager_of_target_user(target_user_id: int, requester: User) -> bool:
    if requester.role == "admin":
        return True
    target_project_ids = await conn.fetch(
        """SELECT project_id FROM project_memberships
            WHERE user_id = $1 AND status = 'active' AND left_at IS NULL""",
        target_user_id)
    for row in target_project_ids:
        if await has_active_project_role(
                row["project_id"], requester.id, min_role="admin"):
            return True
    return False

5.5 プロジェクト離任後の猶予期間判定

基本設計書5.25節の猶予期間ロジックを、5.3節のhas_active_project_roleを拡張する形で実装する。「現役メンバー」または「削除から猶予日数以内」のいずれかを満たせば受講権限を継続する。

async def has_active_project_role(project_id: int, user_id: int, min_role: str) -> bool:
    row = await conn.fetchrow(
        """SELECT role, status, left_at FROM project_memberships
            WHERE project_id = $1 AND user_id = $2""",
        project_id, user_id)
    if row is None:
        return False
    if row["status"] == "active" and row["left_at"] is None:
        return ROLE_RANK[row["role"]] >= ROLE_RANK[min_role]
    if row["left_at"] is not None:
        grace_days = await get_setting_int(
            "project_leave_grace_period_days", default=30)
        if row["left_at"] + timedelta(days=grace_days) >= datetime.now(timezone.utc):
            # 猶予期間中は「受講者」相当のアクセスのみ継続する（編集権限は即時失効）
            return min_role == "learner"
    return False
猶予期間中は受講権限のみ継続する: 基本設計書5.25節の設計判断のとおり、ロール降格そのものは猶予期間の対象外とし、プロジェクトから削除された場合のみ猶予期間が発生する。上記実装ではleft_atが設定された行に対してはmin_role == "learner"のときのみtrueを返すことで、「猶予期間中でも教材の新規編集はできない（即時失効）が、既に配信された教材の閲覧・受講は継続できる」という非対称な扱いを表現している。

5.6 フロントエンド側のガード

frontend/src/App.tsxでA-04（/api/auth/me）の結果とS-11「自分が参加しているプロジェクト」の集計に基づきルート・メニュー表示を制御する。権限の正はサーバー側検証（5.1〜5.5節）であり、以下はUX目的の表示制御に過ぎない。

  • 未認証（A-04が401）→ S-01（/login）へリダイレクト
  • 「教材編集」メニュー: 常時表示（全社員が「全社公開」プロジェクトの編集者を自動的に持つため、実質的に誰でもS-13へ進める。基本設計書4.2節）
  • 「プロジェクト管理」メニュー（S-12への導線）: 自分が管理者であるプロジェクトが1件以上ある場合のみ表示
  • 「受講状況ダッシュボード」（S-08）・「配信設定」（S-06）メニュー: adminは常時表示。member はプロジェクト管理者であるプロジェクトが1件以上ある場合のみ表示（自プロジェクト範囲）
  • 「管理」メニュー（S-10）: adminのみ表示
  • S-19（設問別の回答・結果一覧）へのリンク: S-05・S-17の設問カードで、当該教材のプロジェクトの管理者/編集者、またはadminにのみ表示
重要: フロントエンドのメニュー出し分けはあくまで表示制御（UX目的）であり、権限の正はサーバー側検証（5.1〜5.5節）である。URL直打ちやAPI直接呼び出しが行われても、全APIがauth_helpers.pyの依存関数で検証するため越権操作はできない。
