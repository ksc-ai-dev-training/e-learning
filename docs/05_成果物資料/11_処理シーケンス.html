11. 処理シーケンス

11.1 初回ログイン〜「全社Wiki」プロジェクトへの自動参加（S-01 → S-02）

  1. 【ブラウザ】未認証で/にアクセス → App.tsxがA-04を呼ぶ → 401 → /login（S-01）へリダイレクト
  2. 【ブラウザ】「Googleでログイン」押下 → A-01へ遷移 → Google認証・同意 → A-02へコールバック
  3. 【backend/routers/auth.py】state照合 → トークン交換・IDトークン検証 → ドメイン検証 → T-01 usersをemail検索、未登録のためrole='member'で新規登録（4.1節）
  4. 【backend】同一トランザクションで、is_company_wide=trueのプロジェクトIDに対するT-04 project_memberships行をrole='editor', status='active', joined_at=now()で作成（4.1節・基本設計書5.25節）
  5. 【backend】JWT発行（token_type='session'）→ HttpOnly Cookieに設定 → 構造化ログevent=login（is_new=true）記録 → 302で/へ
  6. 【ブラウザ】App.tsxが再度A-04を呼び200を取得 → S-02（マイ学習）を表示。A-39を呼ぶが、まだ配信設定（assignments）が無いため一覧は空
  7. 【ブラウザ】サイドバーの「教材編集」メニューを押下 → S-13（プロジェクト選択）に「全社Wiki」カードが表示されていることを確認できる（editorとして自動参加済みのため）

11.2 教材新規作成〜Claude Codeでの往復編集（F-05, S-14 → S-05 → Claude Code）

  1. 【ブラウザ】S-14「＋新規教材を作成」押下 → A-16（project_id省略。「全社Wiki」が既定補完）→ 201、下書き教材IDを取得 → S-05へ遷移
  2. 【ブラウザ】S-05目次編集タブでタイトルのみ入力し「下書き保存」→ A-17でtitleを更新
  3. 【利用者端末】Claude CodeでManabi materials get {id}相当のCLIコマンドを実行 → CLIヘルパーが保存済みのCLIトークン（7.1節）でA-19（GET /source）を呼ぶ → フロントマター＋空の本文（目次未作成のためタイトルのみ）をtext/plainで取得
  4. 【利用者】ローカルでMarkdownファイルとして章・小見出し・ページ・問題を執筆（基本設計書8.3節のスキーマに従う）
  5. 【利用者端末】Manabi materials update {id}相当のコマンド → A-20（PUT /source）を実行
  6. 【backend/materials.py】require_material_editorで権限判定 → 7.2節の手順でパース → 7.3節の手順でトランザクション内にてmaterials更新・material_nodes全置換・questions全置換 → T-08へchanged_via='claude_code'で改訂履歴行を追加（7.4節）→ 200で新規採番済みのソーステキストを返す
  7. 【ブラウザ】S-05を再読み込みすると、目次編集タブに新しい章・ページ構成が反映されている（画面とClaude Codeが同一データを共有）
  8. 【ブラウザ】「AIレビュー結果」タブでA-32を実行 → 同期でClaude APIを呼び出し（8.6節F-08）→ 指摘事項一覧を表示
  9. 【ブラウザ】指摘を踏まえて「公開する」押下 → A-17でstatus='published'に更新

11.3 受講〜記述式AI採点〜合否確定（S-04 → S-16 → S-04）

  1. 【ブラウザ】S-02から教材を選びS-04（目次）へ → A-15で目次取得、A-40（mode='graded'）で新規試行を開始
  2. 【ブラウザ】目次からページを選択 → S-16へ遷移。説明文閲覧後、選択式設問に回答するたびA-41で保存
  3. 【ブラウザ】記述式設問に回答し「回答して次のページへ」（最終ページ）→ A-42（提出）を呼ぶ
  4. 【backend/learning.py】選択式設問は即時採点。記述式設問は当該設問のgrading_modeが'ai'のためAI採点ジョブを非同期起動（8.2節）→ プレースホルダとしてanswers.ai_score_pct=NULLのまま200を返す（score_pct・passedは「採点中」を示すNULL）
  5. 【backend/8.2節ジョブ】ai_client.pyがClaude APIへ回答内容・採点基準を送信 → 構造化出力を受け取りanswers.is_correct, ai_score_pct, ai_feedbackを更新 → T-19へ利用ログを記録 → 4.5節A-42と同じロジックでquiz_attempts.score_pct, passedを再計算し確定
  6. 【ブラウザ】S-04に戻り、SWRのポーリングで採点結果が反映されたことを確認（3秒間隔でA-43を再検証）。ドボン問題があればfail_reasonを表示
  7. 【ブラウザ】不合格かつretake_allowed=trueの場合、「再受験する」ボタンを表示 → A-71（retake_scopeに応じて全問または誤答のみを含む新規試行を開始）

11.4 プロジェクトへのメンバー招待〜承諾（S-12 → S-15）

  1. 【ブラウザ】S-12「メンバー管理」タブで社員を検索し初期ロール「編集者」を選択 → A-12を呼ぶ
  2. 【backend】require_project_role(min_role='admin')で権限判定 → 既存行の重複チェック（既に招待/参加済みなら400）→ status='invited'でproject_memberships行を作成 → 構造化ログevent=project_membership_change（action=invite）
  3. 【被招待者・ブラウザ】S-15「招待されているプロジェクト」セクションにA-11（user_id=自分, status=invited）の結果として表示される
  4. 【被招待者・ブラウザ】「承諾」押下 → A-67（{"status": "active"}）→ backendで本人確認 → status='active', joined_at=now()に更新
  5. 【被招待者・ブラウザ】以降、S-13で当該プロジェクトのカードが表示され、教材編集が可能になる（5.2節require_project_roleがstatus='active'を満たすため）

11.5 教材のプロジェクト間共有申請〜承認（F-26、S-12 → S-12）

  1. 【共有元・ブラウザ】S-12「教材の共有」タブで公開済み教材を選び、共有先プロジェクトを指定 → A-60（{"shared_to_project_id": int}）
  2. 【backend】require_project_role(materials.project_id, min_role='admin')で権限判定 → 教材がstatus='draft'なら400 → T-22へstatus='pending'で行を作成（既存rejected行があれば同UNIQUE制約によりON CONFLICT DO UPDATEでpendingに戻す）
  3. 【共有先・ブラウザ】S-12「自プロジェクト宛て共有リクエスト」セクションにA-66（status=pending）の結果として表示される
  4. 【共有先・ブラウザ】「承認」押下 → A-65（{"status": "accepted"}）→ backendでrequire_project_role(shared_to_project_id, min_role='admin')判定 → responded_by, responded_atを設定
  5. 【共有先の受講者・ブラウザ】S-03の当該プロジェクトタブ、S-02のマイ学習に当該教材が表示されるようになる（5.3節条件3・6.1節/6.2節のOR判定がstatus='accepted'を検出するため）

11.6 必修配信〜未受講者へのSlack催促（F-11・F-12、S-06 → S-08）

  1. 【admin・ブラウザ】S-06で対象教材を選び、配信対象「全社」・区分「必修」・期限を設定 → A-38（scope_type='company', required=true）→ backendでadmin限定チェック（4.4節callout）→ 保存
  2. 【全社員・ブラウザ】S-02（マイ学習）で当該教材が必修一覧に表示される（A-39が新しいassignments行を反映）
  3. 【admin・ブラウザ】期限が近づいた時点でS-08を開く → A-45（scope='company'）でダッシュボード取得 → A-46で未受講者一覧取得
  4. 【admin・ブラウザ】未受講者を選択し「Slackで催促」押下 → A-47（{"assignment_id", "user_ids"}）
  5. 【backend/dashboard.py】対象者ごとにT-20 slack_notification_logsを参照し24時間以内の送信済みをスキップ（4.6節callout）→ 未送信の対象者へslack_client.py経由でWebhook送信 → 送信結果（sent/failed）をT-20へ記録 → {"sent": N, "skipped": M}を返す

11.7 表示名・アイコンの自己編集（F-29、S-15）

  1. 【ブラウザ】S-15を開く → A-04で現在のname・picture_urlを取得し表示名欄・アイコンに反映
  2. 【ブラウザ】表示名欄を「佐藤 健一」から「佐藤 健一（新人研修担当）」に編集し「保存」押下 → A-75（{"name": "佐藤 健一（新人研修担当）"}）
  3. 【backend/routers/auth.py】require_auth → nameが1〜100文字であることを検証 → T-01 users.nameを更新 → 200で更新後の値を返す
  4. 【ブラウザ】続けてアイコン画像ファイルを選択 → A-76（{"filename", "mime_type": "image/jpeg", "size_bytes"}）→ 200でupload_url・storage_keyを取得
  5. 【ブラウザ】取得したupload_urlへファイルを直接PUT（Supabase Storageへ、バックエンドを経由しない）
  6. 【ブラウザ】アップロード成功後、A-75（{"icon_storage_key": storage_key}）を呼び確定 → backendはstorage_keyが当該ユーザー宛てに発行されたものであることを検証しcustom_picture_keyを更新 → 200
  7. 【ブラウザ】以降、A-04・サイドバーのアバター表示はcustom_picture_keyから生成した署名付きURLを表示する
  8. 【本人・後日】Googleアカウント側のプロフィール名を変更してもログイン時に上書きされないことを確認（3.1節・4.1節A-02処理フロー参照）。元に戻したい場合はS-15で「Googleの画像に戻す」→ A-77を呼びcustom_picture_keyをNULLに戻す
