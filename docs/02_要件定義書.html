2. 業務要件

本システムが支える学習の流れは以下のとおりである。教材作成者が教材を作りプロジェクトの管理者・編集者が教材を作り、AIレビューを経て公開し、受講者が必修・任意の教材を受講する。学習記録はAIによる分析を経て、教材作成者・管理者プロジェクトの管理者・編集者に還元される。

  • 教材作成者（教育担当に限らない社員、REQ-F-04）は、画面またはClaude Codeでテキスト形式の教材を作成し、AIレビューを経て公開する。教材は必ずいずれかのプロジェクトに属する（REQ-F-04・F-25）。プロジェクトの編集者・管理者（教育担当に限らない社員、7.3参照）は、画面またはClaude Codeでテキスト形式の教材を作成し、AIレビューを経て公開する。
  • 教材にはオーナー（既定は作成者本人）を設定する。プロジェクト単位の教材は、オーナーの異動・離任後も管理者が共同編集者を追加したりオーナーを引き継いだりでき、メンテナンスが特定個人に依存し続けない。教材の編集権限はプロジェクトの管理者・編集者（ローカルロール）が持つため、特定個人の異動・離任に依存しない（7.3参照）。個人だけで教材を作りたい場合も、まず自分がプロジェクトを作成する必要がある（作成者は自動的にそのプロジェクトの管理者になる）。
  • 管理者は、公開された教材の受講対象（全社・部署・プロジェクト・個人）と必修/任意区分を設定し、必修教材には受講期限を設ける。プロジェクト単位の配信対象・必修/任意・期限は、そのプロジェクトの管理者も設定できる。
  • 受講者は、必修教材を期限までに、任意教材は自由なタイミングで受講する。選択式・記述式の問題に回答し、中断しても次回続きから再開できる。
  • 合否判定を伴う受験とは別に、習熟のための反復演習・誤答抽出出題をいつでも利用できる。
  • 部署長/PM・管理者は、担当範囲の受講状況を確認し、未受講者にはSlackで受講を促す。管理者（全社）・プロジェクト管理者（自プロジェクト）は、担当範囲の受講状況を確認し、未受講者にはSlackで受講を促す。
  • AIは記述式回答の採点、正答率の低い設問の分析、受講者個人へのフィードバック、組織単位のレポート作成を行う。分析結果は教材作成者・管理者プロジェクトの管理者・編集者に還元され、教材改訂につながる。

F-22AI個人フィードバック受講者ごとの回答傾向から、理解不足の点や次に学ぶとよい教材を本人に示す。REQ-F-18
F-23AI組織レポート生成部署・プロジェクト単位プロジェクト単位・全社単位の学習状況・習熟度の傾向を、数値の一覧に加え要約と示唆を含むレポートとしてまとめる。REQ-F-19
F-24プロジェクト管理プロジェクトは誰でも新規作成できる。作成者はそのプロジェクトの管理者となり、プロジェクト情報（名称・説明等）の編集、メンバーの追加・削除、メンバーのロール（管理者/編集者/受講者）の設定を行う（7.3参照）。※運用上は、部署長・PMがプロジェクトを作成して管理者となることを想定するが、システムとしては作成者を限定しない。REQ-F-06
F-25プロジェクト単位教材管理教材は必ずいずれかのプロジェクトに紐づけて管理する（個人所有の教材は存在しない。v1.5でF-07を統合）。個人で教材を作りたい場合は、まず自分のプロジェクトを作成する（作成者は自動的にそのプロジェクトの管理者になる、F-24）。教材の編集権限は、そのプロジェクトの管理者・編集者（ローカルロール）が持つ。受講権限は、そのプロジェクトの受講者、および配信設定（F-09）で別途対象に指定された利用者が持つ。REQ-F-01, REQ-F-04, REQ-F-06
F-26教材のプロジェクト間共有あるプロジェクトに紐づく教材を、別のプロジェクトでも受講・参照できるよう共有できる。共有の可否を判断・実行する権限は、教材が紐づく元プロジェクトの管理者が持つ。REQ-F-06
反復演習（F-16）は合否判定を伴う受験（F-14）とは区別して記録し、反復演習の結果は合否に影響しない。受講者が気兼ねなく繰り返し学習できることを狙いとする（REQ-F-12）。
コード記述式問題（F-13・F-20）の対象範囲: 数式処理・辞書操作等、想定される入出力をAIが読解のみで正しく推論できる程度の教育用の課題を主な対象とする。採点はコードを実際に実行するのではなく、AIによる静的な読解（コードを読んで動作を推論する）で行う。ループが多く実行結果の予測が難しい処理や、精密な数値計算・大量データ処理を伴う課題では、AIの推論精度が下がるため、そうした課題を出題する場合は誤判定のリスクを踏まえた運用（人による採点結果の確認・修正、REQ-F-16）を徹底する。コードの実行・自動テスト（サンドボックス実行環境）は対象外とする（3.2節参照）。
権限モデルの簡素化（v1.5）: システム全体のロールを admin（管理者）／一般ユーザーの2種に統合し、受講者(learner)・教材作成者(author)・部署長/PM(manager) の3ロールは廃止した。教材の編集・受講権限、および受講状況の確認範囲は、すべてプロジェクトのローカルロール（管理者/編集者/受講者、7.3参照）で判定する。あわせて教材は必ずいずれかのプロジェクトに属する方式（F-25）に一本化し、個人所有の教材（オーナー・共同編集者モデル、F-07）は廃止した。部署（department）の概念もシステムから廃止し、組織単位は「全社」「プロジェクト」「個人」の3種となる。詳細は7章を参照。

5. 教材連携要件（Claude Code連携）

REQ-F-02は「本システムの最も重視する要求」とされており、教材作成者プロジェクトの編集者・管理者がClaude Codeで作成した教材を、画面での再入力なしにシステムへ反映できることを目的とする。以下の4点を満たす（F-05）。

#満たすべき要件
1教材・問題をテキスト形式（MarkdownまたはHTML）で記述できること
2手元のファイルの登録・更新が、画面操作を介さず実行できること
3システム上の既存教材を取得して修正し、システムへ戻せること（往復できること）
4教材の改訂履歴が残り、いつ誰が何を変更したかを追えること

5.1 連携方式

項目内容
記述形式MarkdownまたはHTML本文＋フロントマター（所属プロジェクト、単元/コース、公開状態、問題定義等のメタデータ）。教材ごとにどちらの形式で記述するかを選べる。教材は必ずいずれかのプロジェクトに属するため、フロントマターで所属プロジェクトを指定する（F-25）。
登録・更新経路認証されたAPI経由。Claude Codeからファイルの登録・更新を画面操作なしに実行できること。
取得（往復）既存教材をテキスト形式で取得できるAPIを用意し、取得→修正→書き戻しの往復を可能にする。
改訂履歴変更のたびに版を記録し、いつ・誰が・何を変更したかを一覧・差分で確認できる。
HTML形式で記述された教材は、スクリプト等の実行可能なコンテンツを無害化（サニタイズ）した上で表示する。任意のHTMLをそのまま描画すると、他の受講者に対するスクリプト実行（XSS）のおそれがあるため。許可するタグ・属性は許可リスト方式とし、<script>・インラインイベントハンドラ（onclick等）・外部ドメインを指定した<iframe>等は原則として許可しない。許可リストの詳細は基本設計フェーズで定める。
この往復インターフェースは、F-21（AIつまずき分析・教材改善提案）の分析結果をもとに教材をClaude Codeで改訂し、再びシステムへ書き戻す循環（つまずき分析 → 改善提案 → Claude Codeでの修正 → 往復登録）を成立させる基盤となる。

6.2 共通方針

  • 非同期処理: 受講者の学習操作をブロックしうる経路（F-20の採点等）は非同期ジョブとして実行し、処理失敗時はリトライする。失敗しても学習記録（回答内容そのもの）は失われない（REQ-N-05）。
  • 入出力の保存: AIへの入力・出力は原則として保存しない。ただしF-20の採点結果（点数・講評）は、人が確認・修正できる必要があるため学習記録の一部として保存する（REQ-F-16）。
  • 利用量の記録: トークン数・概算コストを記録し、管理者が確認できる。質問・回答等の内容そのものは記録しない（Keirekiのai_usage_logsと同様の方式）。
  • モデル選択: 利用するモデルは管理画面から選択でき、画面設定 > 環境変数 > 既定値の順で優先する（Keirekiと同様）。
  • 送信データの範囲: 教材本文・問題・回答内容・集計データを送信対象とし、個人が特定される情報は必要な範囲に留める。詳細は基本設計フェーズで定める。

AI利用記述式採点・分析等は外部AI APIの利用を前提とする。利用には費用が発生し、教材・回答内容等の社内情報を外部へ送信することを踏まえた運用とする。具体的な連携方式は6章を参照。
監査教材の改訂、配信設定の変更、ユーザーのロール変更を構造化ログ・改訂履歴として記録する。

9.2 前提条件

  • 組織情報の扱い: 部署・プロジェクトの構成情報は、現時点で他システムから参照できる形では存在しないため（要求仕様の制約条件）、本システム内にマスタとして保持する（F-03）。プロジェクトの構成情報は、現時点で他システムから参照できる形では存在しないため（要求仕様の制約条件）、本システム内にマスタとして保持する（F-24）。部署（department）はv1.5でシステムの概念として廃止したため、組織単位は「全社」「プロジェクト」「個人」の3種となる。プロジェクトは誰でも新規作成でき、作成者がそのプロジェクトの管理者になる。プロジェクトへのメンバー追加・削除およびロール（管理者/編集者/受講者）の設定は、そのプロジェクトの管理者が行う（7.3参照）。管理者による設定の反映が遅れたり対応が漏れたりする場合に備え、プロジェクトを離任した場合（管理者がメンバーを削除した場合を含む）も一定期間（猶予期間。日数は基本設計フェーズで定める）は旧プロジェクトの教材への閲覧アクセスを継続し、急なアクセス喪失を避ける。他システム（プロジェクト管理システム等）とのAPI連携によるプロジェクト所属情報の自動取得（Claude Code経由を含む）は、参照可能な外部システムが現時点で存在しないため初期実装の対象外とし、将来そうしたシステムが整備された場合の拡張として検討する。
  • 想定規模: 社員200名程度を想定する。全社必修教材の配信直後にアクセスが集中することを踏まえた構成とする。
  • 教材・問題の項目定義: 本文構成、問題形式の詳細等は基本設計書で定める。
  • ファイル容量の上限: 動画・スライド等のファイルサイズ・保存容量の上限は、利用するストレージサービスの無料枠等の制約を踏まえ、基本設計フェーズで定める。
  • AI利用の運用ルール: AI APIへ送信するデータの範囲、および利用費用の管理方法は別途整理する。

10. 実装スコープ（フェーズ分け）

本書の3章・5章・6章は要求仕様書の全要求（REQ-F-01〜REQ-F-19、REQ-N-01〜REQ-N-06）を過不足なく要件化したものであり、機能を絞ったものではない。一方、規模が大きく、限られた期間での実装を前提とする場合、全機能を一度に作ることは現実的ではない。本章では、フェーズ0〜5に分けて開発順序を示す。要求仕様書自体が「最も重視する要求」（REQ-F-02）「重要な要求」（REQ-F-08）と明記している機能を早いフェーズに置き、他機能の前提となる機能（組織マスタ F-03プロジェクト管理 F-24、学習記録 F-18 等）は、それに依存する機能より先行させる。
